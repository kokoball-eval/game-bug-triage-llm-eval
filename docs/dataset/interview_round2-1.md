## A1. 커뮤니티 원문의 품질 비율

**답변 요지** — 커뮤니티 원문 기준 비율은 다음과 같다.

| 명확 | 단문 | 감정적 불만 | 복합 | 중복 | 문의·건의 | 욕설·무관한 글 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1% | 20% | 24% | 10% | 10% | 5% | 30% |

## A2. 커뮤니티 제보를 BTS로 옮길 때의 기준

**답변 요지** — 반복적으로 나오지 않는 일회성 불만, 재현을 시도할 수 없을 만큼 정보가 부족한 제보, 이미 등록된 이슈는 BTS에 옮기지 않고 폐기했다.

## B1. QA 이슈 작성 양식

**답변 요지** — QA 이슈는 다음 다섯 칸으로 작성했다. 이미지·영상·로그는 이슈 등록 화면에서 바로 첨부할 수 있었다.

| 칸 | 작성 내용 |
| :--- | :--- |
| `[테스트 환경]` | PC·모바일 구분과 테스트한 빌드 버전 |
| `[이슈 설명]` | 이슈 현상에 대한 상세 정보 |
| `[기대 결과]` | 이슈가 없을 때 명세서 기준의 정상 동작. 수정 방향을 적는 칸이며, 개선이 필요한 경우 여기에 제안을 적기도 한다 |
| `[실제 결과]` | 재현을 시도했을 때 실제로 나온 결과 |
| `[참고 문서]` | 기획서, 관련 문서 링크 |

> 후속 확인(전체 검토): 실무 양식에는 **재현율** 칸도 있었다 → v1.3 트랙 B 입력에 `[재현율]` 칸을 추가했다.

## B2. 우선순위 오판·정보 누락으로 반려되던 사례

**답변 요지** — 주로 주니어 QA의 실수였고, 평가 문항으로 옮길 만큼 구체적인 사례는 기억나지 않는다. → 이 유형은 v1.3 문항으로 만들지 않았다.

## C1. 크로스플랫폼 특이 버그

**답변 요지** — 특정 기기 모델에서만 발생하는 이슈가 많았고, 주로 해상도·UI 스케일 문제나 접속 문제였다.

## C2. 사람이 반드시 봐야 하는 건의 기준

**답변 요지** — 프로세스상 모든 이슈는 재현을 확인한 뒤 넘겼다. 단, Critical 이슈는 빠르게 처리해야 하므로 먼저 전달하고 재현을 시도했다.

## 2차 인터뷰로 정한 것 (해석 — 3차 인터뷰에서 확인)

| 항목 | 해석 | 근거 |
| :--- | :--- | :--- |
| 트랙 A의 핵심 업무 | **걸러내기**. 원문의 64%(욕설·무관 30 + 감정적 불만 24 + 중복 10)는 등록 대상이 아닐 가능성이 크고, 명확한 제보는 1%뿐 | A1 |
| 자동화가 대신하는 범위 | **읽고·거르고·티켓을 쓰는 일**. 재현은 대신하지 않는다. 실무에서는 모든 이슈를 사람이 재현한 뒤 넘겼으므로, 자동 등록 티켓은 "재현 대기" 상태로 들어간다 | C2 |
| Critical 처리 | Critical 후보는 재현 전에 먼저 전달(실무의 "우선 전달 후 재현"을 따름). 당시 이름은 `즉시 전달`이었고, 전체 검토에서 리드 QA 사인을 거치는 `긴급 사인 요청`으로 바뀌었다 | C2 |
| 트랙 B 입력 형식 | `[테스트 환경] [이슈 설명] [기대 결과] [실제 결과] [참고 문서]` 5개 섹션 | B1 |
| 단일 제보의 한계 | "반복되는 문제인가"는 제보 1건만 보고는 알 수 없다 → 트랙 A에서 일회성 여부는 판정하지 않고, 같은 내용의 제보를 묶는 일은 v2.0(중복 감지, RAG)에서 다룬다 | A2 |
