# v1.3 평가셋 설계 인터뷰 — 3차 (기준서 초안 확인)

> 2026-10-01 · [기준서 초안](triage_guideline.md)의 확인 질문 4개에 대한 답변

## 1. 지형 꼼수 공략(P-B4)의 "버그 아님"은 문의·건의로 받을까, 따로 둘까?

**답변 요지** — "버그 아님"은 문의·건의와 별도 분류로 두는 것이 적절하다.

→ `[분류]`에 **버그 아님**을 추가 (C-7).

## 2. 트랙 A의 "재현 정보 충분" 기준을 플랫폼·기기 + 발생 상황으로 잡아도 되나? (빌드 버전 필수 제외)

**답변 요지** — 기준이 적절하다. 유저는 빌드 버전을 확인할 수는 있지만 대부분 알지 못한다. 실무에서는 제보가 등록된 날짜를 업데이트 일정과 대조해 빌드를 판별했다.

→ R-2 확정. 빌드는 **게시 일시와 업데이트 일정으로 추정**하므로 누락 정보로 요청하지 않는다 (R-5). 트랙 A 입력에 게시 일시를 넣는다.

## 3. 문의·건의를 폐기하고 운영·CS 전달을 권장하는 처리가 맞나?

**답변 요지** — 처리 순서가 실무와 다르다. 실무에서는 운영/CS가 이슈를 BTS에 등록해 개발사로 전달하고, 개발 QA는 실제로 재현되는지 확인한 뒤 대응 여부를 결정했다. 대응하는 경우 수정과 수정 확인을 마친 뒤 빌드에 반영해 전달하고, 운영/CS가 최종 확인 후 이슈를 종료했다.

→ 커뮤니티 제보를 BTS에 **등록하는 주체는 운영/CS**이고, 개발 QA는 재현 확인과 대응 여부 결정을 맡는다. 트랙 A 자동화는 **운영/CS의 등록 단계**를 돕는 것으로 위치를 바로잡는다 (§0 이슈 생명주기). 문의·건의는 BTS에 올리지 않고 운영/CS가 직접 응대한다 → `[처리]`에 **CS 응대**를 추가 (H-6).

## 4. "애매하면 폐기보다 보류" 원칙이 실무 감각과 맞나?

**답변 요지** — 실무 감각과 맞다. 반복적으로 보이는 이슈는 보류 상태로 두고 재현 여부를 주기적으로 확인했으며, 지속적으로 제보되지 않으면 폐기하기도 했다. 확인·폐기 주기가 길어도 비용 부담은 크지 않았고, 계속 보류로 두는 경우도 있었다.

→ H-9 확정. 보류의 비용은 낮고, 진짜 결함을 버리는 비용이 크다. 보류 건의 "지속 제보 여부" 판단은 여러 제보를 묶어야 하므로 v2.0(중복 감지)에서 다룬다.
