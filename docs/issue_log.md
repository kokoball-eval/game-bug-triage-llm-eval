| 항목 | 내용 |

## ISSUE-002 · 허용폭과 정확히 같은 변화가 FAIL 판정됨 (부동소수점 경계값)

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 경계값에서만 발생하는 잘못된 FAIL |
| 발견 | 2026-09-30, 단위 테스트 작성 중 (경계값 분석) |
| 조치 커밋 | `1936444` |
| 회귀 테스트 | `tests/test_compare_runs.py::test_exactly_at_tolerance_passes` |

**현상** — 평균 지연이 허용폭(+20%)과 **정확히 같게** 늘어난 경우 통과해야 하는데 FAIL이 났습니다. 화면에는 "변화 +20.0% (허용 악화폭 20.0%)"로 표시되면서 FAIL이 뜨는, 보는 사람에게는 모순인 결과였습니다.

**원인** — `(1.668 − 1.39) / 1.39 × 100`이 이진 부동소수점에서는 `20.000000000000004`로 계산되어 `≤ 20.0` 비교에서 거짓이 됐습니다. 화면 표시는 소수 첫째 자리로 반올림하고 비교는 반올림 없이 하고 있어서, **보이는 값과 판정에 쓰는 값이 서로 달랐습니다.**

**조치** — 변화율을 소수 둘째 자리로 반올림한 뒤 허용폭과 비교합니다. 반올림에는 문서 수치와 같은 half-up 함수(`summarize_eval.rnd`)를 씁니다.

**재발 방지** — 경계값 테스트를 회귀 테스트로 남겼습니다. 반올림을 빼는 변경을 일부러 넣어 보면 이 테스트가 실패하는 것까지 확인했습니다.

## ISSUE-005 · README 굵은 글씨 깨짐, 표 칸 안 줄바꿈

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Trivial — 표시 문제 |
| 발견 | 2026-09-30, GitHub 화면에서 README를 직접 확인하다 발견 |
| 조치 커밋 | `9773f3a` |

**현상**
1. `**"LLM에게 … 평가 체계"**로`가 굵게 표시되지 않고 `**` 기호가 그대로 보였습니다. 1절의 `**"Aether Raid"**의`도 같은 문제가 있었습니다.
2. 로드맵 표의 "상태" 칸이 좁아 `완료`가 `완/료`로 쪼개져 표시됐습니다.

**원인**
1. 마크다운(CommonMark)은 **닫는 `**` 바로 앞이 문장부호(`"`)이고 바로 뒤가 글자(`로`)이면 굵은 글씨로 인식하지 않습니다.** 영어는 보통 뒤에 공백이 오지만, 한국어는 조사가 바로 붙어서 이 규칙에 자주 걸립니다.
2. 한국어는 글자 단위로 줄이 바뀔 수 있어서, 좁은 표 칸에서 단어가 쪼개집니다.

**조치**
1. 따옴표를 굵은 글씨 밖으로 뺐습니다: `"**…평가 체계**"로`
2. 상태를 버전 앞 아이콘으로 합쳤습니다(`✅ v1.0`). 아이콘과 버전 사이에는 줄바꿈 없는 공백(`&nbsp;`)을 넣었습니다.

**재발 방지** — README를 고칠 때 마크다운 렌더러로 전체 파일을 변환해서 풀리지 않은 `**`이 0개인지 확인합니다.

## ISSUE-006 · 환각 탐지기 오탐 2건 (출시 전 단위 테스트에서 발견)

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 근거 있는 응답을 날조로 오판 (게이트가 정상 응답을 FAIL 낼 수 있음) |
| 발견 | 2026-10-01, v1.2 환각 탐지기 단위 테스트 작성 중 (커밋 전) |
| 회귀 테스트 | `tests/test_detect_hallucination.py::test_fact_present_in_input_is_grounded`, `::test_quantity_must_match_exactly` |

**현상**
1. 입력에 "v2.3.1"이 있고 응답이 "v2.3.1 회귀 테스트 권장"이라고 쓰면, 버전 번호 일부와 "회귀"의 "회"가 합쳐져 **"3.1 회"라는 횟수**로 뽑히고 날조로 판정됐습니다.
2. 입력이 "15초 후에 멈춤"이면 응답의 **"5초"가 근거 있음**으로 판정됐습니다. "15초"라는 글자 안에 "5초"가 들어 있기 때문입니다.

**원인** — 수치 패턴이 앞뒤 문맥을 보지 않았습니다. 1번은 숫자 앞의 마침표(버전 번호의 일부)와 단위 뒤의 글자("회귀")를, 2번은 근거를 찾을 때 숫자 앞에 다른 숫자가 붙어 있는지를 확인하지 않았습니다.

**조치** — 수치 패턴에 "앞에 숫자·마침표가 붙지 않을 것", "`회` 뒤에 `귀`가 오지 않을 것"을 추가하고, 수치의 근거 확인도 "앞에 숫자가 붙지 않은 같은 수치"가 입력에 있을 때만 인정하도록 바꿨습니다.

**재발 방지** — 두 경우를 테스트로 고정했습니다. 수정 후 실제 로그 85건에서 탐지 결과가 기대(Llama Q08 4건, 그 외 0건)와 같은 것도 다시 확인했습니다.

> 지금까지의 실제 로그 85건에는 두 형태가 없어 수치에 영향을 준 적은 없습니다. 다만 "v2.3.1 회귀 테스트 권장"은 트리아지 응답에서 흔한 표현이라, 그대로 두었다면 평가셋을 늘리는 v1.3에서 정상 응답을 FAIL로 만들었을 가능성이 높습니다.

## OBS-001 · 측정 환경 차이로 성능 지표가 크게 흔들림 (관찰 사항)

| 항목 | 내용 |
| :--- | :--- |
| 구분 | 관찰 사항 — 모델이 아니라 측정 환경의 변화 |
| 발견 | 2026-09-30, 첫 회귀 판정 분석 |
| 대응 | v1.2 — 실행 전 자동 점검(`src/preflight.py`) + README 4-7) 체크리스트 |

**현상** — 재실행에서 대조군 Llama-3.1-8B의 평균 지연이 +45.6%, 생성 속도가 −32.5% 나빠져 회귀 기준에서 FAIL이 났습니다. 1회차에는 30 t/s대까지 떨어졌다가 2회차에 49 t/s로 회복됐고, Qwen 워밍업 로딩도 v1.0의 2.1초에서 15.9초로 늘었습니다.

**분석** — `run_config`의 모델 digest가 v1.0과 같아(`46e0c10c039e`), 모델 파일은 바뀌지 않았습니다. 같은 GPU를 쓰는 다른 프로그램, 전원 모드, 디스크 캐시 상태 같은 **측정 환경 차이**가 원인일 가능성이 높습니다. 게이트가 모델 회귀가 아닌 환경 변화까지 잡아낸 사례이기도 합니다.

**결과 (2026-10-01)** — 다른 프로그램이 VRAM을 거의 쓰지 않고(362~485 MiB) 전원이 연결된 상태에서 다시 측정하니 Llama 평균 속도가 64.3 t/s로 v1.0(66.56 t/s) 수준에 돌아왔습니다(9/30 재실행 44.9 t/s). 모델이 아니라 측정 환경 차이가 원인이었다는 해석을 뒷받침하므로 이 관찰을 종료합니다.

**v1.2 대응** — `run_eval.py`가 모델을 호출하기 전에 GPU 점유(Ollama 외 VRAM 1,024 MiB 이상이면 경고)와 전원 연결 상태를 점검해 로그(`run_config.environment`)에 남기고, `--strict-env`를 주면 경고가 있을 때 실행하지 않습니다. `compare_runs.py`는 두 실행의 환경 경고와 전원 상태 차이를 함께 보여 줍니다. 위 결과로 확인을 마쳤습니다.
