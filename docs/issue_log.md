## ISSUE-002 · 허용폭과 정확히 같은 변화가 FAIL 판정됨 (부동소수점 경계값)

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 경계값에서만 발생하는 잘못된 FAIL |
| 발견 | 2026-09-30, 단위 테스트 작성 중 (경계값 분석) |
| 조치 커밋 | `1936444` |
| 회귀 테스트 | `tests/test_compare_runs.py::test_exactly_at_tolerance_passes` |

**현상** — 평균 지연이 허용폭(+20%)과 **정확히 같게** 늘어난 경우 통과해야 하는데 FAIL이 났습니다. 화면에는 "변화 +20.0% (허용 악화폭 20.0%)"로 표시되면서 FAIL이 뜨는, 보는 사람에게는 모순인 결과였습니다.

**원인** — `(1.668 − 1.39) / 1.39 × 100`이 이진 부동소수점에서는 `20.000000000000004`로 계산되어 `≤ 20.0` 비교에서 거짓이 됐습니다. 화면 표시는 소수 첫째 자리로 반올림하고 비교는 반올림 없이 하고 있어서, **보이는 값과 판정에 쓰는 값이 서로 달랐습니다.**

**조치** — 변화율을 소수 둘째 자리로 반올림한 뒤 허용폭과 비교합니다. 반올림에는 문서 수치와 같은 half-up 함수(`summarize_eval.rnd`)를 씁니다.

**재발 방지** — 경계값 테스트를 회귀 테스트로 남겼습니다. 반올림을 빼는 변경을 일부러 넣어 보면 이 테스트가 실패하는 것까지 확인했습니다.

## ISSUE-005 · README 굵은 글씨 깨짐, 표 칸 안 줄바꿈

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Trivial — 표시 문제 |
| 발견 | 2026-09-30, GitHub 화면에서 README를 직접 확인하다 발견 |
| 조치 커밋 | `9773f3a` |

**현상**
1. `**"LLM에게 … 평가 체계"**로`가 굵게 표시되지 않고 `**` 기호가 그대로 보였습니다. 1절의 `**"Aether Raid"**의`도 같은 문제가 있었습니다.
2. 로드맵 표의 "상태" 칸이 좁아 `완료`가 `완/료`로 쪼개져 표시됐습니다.

**원인**
1. 마크다운(CommonMark)은 **닫는 `**` 바로 앞이 문장부호(`"`)이고 바로 뒤가 글자(`로`)이면 굵은 글씨로 인식하지 않습니다.** 영어는 보통 뒤에 공백이 오지만, 한국어는 조사가 바로 붙어서 이 규칙에 자주 걸립니다.
2. 한국어는 글자 단위로 줄이 바뀔 수 있어서, 좁은 표 칸에서 단어가 쪼개집니다.

**조치**
1. 따옴표를 굵은 글씨 밖으로 뺐습니다: `"**…평가 체계**"로`
2. 상태를 버전 앞 아이콘으로 합쳤습니다(`✅ v1.0`). 아이콘과 버전 사이에는 줄바꿈 없는 공백(`&nbsp;`)을 넣었습니다.

**재발 방지** — README를 고칠 때 마크다운 렌더러로 전체 파일을 변환해서 풀리지 않은 `**`이 0개인지 확인합니다.

## ISSUE-006 · 환각 탐지기 오탐 2건 (출시 전 단위 테스트에서 발견)

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 근거 있는 응답을 날조로 오판 (게이트가 정상 응답을 FAIL 낼 수 있음) |
| 발견 | 2026-10-01, v1.2 환각 탐지기 단위 테스트 작성 중 (커밋 전) |
| 회귀 테스트 | `tests/test_detect_hallucination.py::test_fact_present_in_input_is_grounded`, `::test_quantity_must_match_exactly` |

**현상**
1. 입력에 "v2.3.1"이 있고 응답이 "v2.3.1 회귀 테스트 권장"이라고 쓰면, 버전 번호 일부와 "회귀"의 "회"가 합쳐져 **"3.1 회"라는 횟수**로 뽑히고 날조로 판정됐습니다.
2. 입력이 "15초 후에 멈춤"이면 응답의 **"5초"가 근거 있음**으로 판정됐습니다. "15초"라는 글자 안에 "5초"가 들어 있기 때문입니다.

**원인** — 수치 패턴이 앞뒤 문맥을 보지 않았습니다. 1번은 숫자 앞의 마침표(버전 번호의 일부)와 단위 뒤의 글자("회귀")를, 2번은 근거를 찾을 때 숫자 앞에 다른 숫자가 붙어 있는지를 확인하지 않았습니다.

**조치** — 수치 패턴에 "앞에 숫자·마침표가 붙지 않을 것", "`회` 뒤에 `귀`가 오지 않을 것"을 추가하고, 수치의 근거 확인도 "앞에 숫자가 붙지 않은 같은 수치"가 입력에 있을 때만 인정하도록 바꿨습니다.

**재발 방지** — 두 경우를 테스트로 고정했습니다. 수정 후 실제 로그 85건에서 탐지 결과가 기대(Llama Q08 4건, 그 외 0건)와 같은 것도 다시 확인했습니다.

> 지금까지의 실제 로그 85건에는 두 형태가 없어 수치에 영향을 준 적은 없습니다. 다만 "v2.3.1 회귀 테스트 권장"은 트리아지 응답에서 흔한 표현이라, 그대로 두었다면 평가셋을 늘리는 v1.3에서 정상 응답을 FAIL로 만들었을 가능성이 높습니다.

<a id="obs-002"></a>
## OBS-002 · 같은 seed에서도 응답이 재현되지 않는 조건 (관찰 사항)

| 항목 | 내용 |
| :--- | :--- |
| 구분 | 관찰 사항 — 측정 절차의 전제 조건 |
| 발견 | 2026-10-02, ISSUE-007 seed 3쌍 측정 |
| 대응 | README 4-7) 측정 절차에 반영 |

**현상** — 프롬프트 v2.3을 seed 11·21로 다시 측정했을 때, 프롬프트와 seed가 같은데도 첫 응답 64개 중 40개(seed 11), 50개(seed 21)가 이전 측정과 달랐습니다.

**분석** — 이 두 측정은 같은 Ollama 프로세스에서 다른 프롬프트(v2.4)를 처리한 직후에 실행됐습니다. 반면 모델을 새로 불러온 상태이거나 직전에 같은 프롬프트를 처리한 상태에서는 첫 응답이 64/64 일치했습니다(seed 1·11·21 각각 두 번 이상 확인). 직전에 처리한 프롬프트의 캐시 상태에 따라 계산 경로가 달라지는 것으로 보입니다.

**결론** — v1.2에서 확인한 "같은 seed면 응답이 재현된다"는 **직전에 다른 프롬프트를 처리하지 않은 상태**에서 성립합니다. 프롬프트를 바꿔 가며 측정할 때는 실행 전에 `ollama stop <모델>`로 모델을 내린 뒤 측정합니다.

<a id="issue-008"></a>
## ISSUE-008 · 날조 탐지기가 같은 수량의 다른 단위 표현을 날조로 판정

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 날조 건수가 실제보다 많게 집계됨 (근거 있는 응답을 날조로 판정) |
| 발견 | 2026-10-02, v1.3 평가용 세트 최종 측정 ([`report/eval_v13_final.md`](../report/eval_v13_final.md) 4절) |
| 근거 | `data/results/v13/history/v13_test_20261002_161508.json` — qwen2.5:7b S17 1·2회차 |
| 상태 | 미수정 (v1.4) |

**현상** — S17 입력은 "100번 뽑았는데", "추석 픽업 100연 돌렸는데"이고, 응답 요약은 "추석 픽업 100회 돌렸으나"이다. 같은 수량을 다른 단위 말로 옮긴 것인데 날조 응답으로 집계됐다.

**원인** — `src/triage_eval/common/detect_hallucination.py`는 수치(quantity)를 "숫자 + 단위" 문자열이 입력에 그대로 있는지로 판정한다. "5초"와 "15초"를 구분하기 위해 붙여 쓴 형태 전체를 비교하므로, 입력의 "100번"·"100연"과 응답의 "100회"는 다른 수치로 처리된다. 횟수를 나타내는 단위 표현(회·번·연)이 서로 같은 뜻이라는 정보가 없다.

**조치하지 않은 이유** — 이 측정 전에 "결과를 보고 프롬프트·안전장치·채점기를 고치지 않는다"고 정했다. 탐지기를 고치면 v1.3 최종 수치가 바뀌므로, 측정값(날조 2건)은 그대로 기록하고 오탐이라는 판단과 근거를 함께 남긴다.

**v1.4 조치 계획** — 횟수 단위(회·번·연)를 같은 단위로 정규화해 비교하고, 이 사례(같은 수량, 다른 단위)와 반대 사례(다른 수량, 같은 단위 — "10회"와 "100회")를 회귀 테스트로 고정한다. 수정 전후로 저장된 실행 기록 전체의 탐지 결과를 비교해 다른 판정이 바뀌지 않는지 확인한다.

<a id="kl-003"></a>
## KL-003 · 평가용 세트에서 판단 정확도 하락 — 프롬프트가 개발용 문항에 맞춰짐 (알려진 한계)

| 항목 | 내용 |
| :--- | :--- |
| 구분 | 알려진 한계 (Known Limitation) |
| 발견 | 2026-10-02, v1.3 평가용 세트 최종 측정 |
| 근거 | [`report/eval_v13_final.md`](../report/eval_v13_final.md) |
| 대응 | v1.4 (판단 기준 일반화), v1.5 (위험 건 검토 큐) |

**현상** — 형식·절차 지표는 개발용과 평가용 모두에서 유지됐으나(허용 값 위반·출력 언어 위반·결함 폐기 0건, 형식 STRICT 100%), 모델 판단에 달린 지표는 크게 낮아졌다.

| 지표 (qwen2.5:7b) | 개발용 | 평가용 |
| :--- | :---: | :---: |
| 우선순위 정답률 | 62.5% | 43.5% |
| X-1 누락 (Critical 미상신) | 2 / 22 | 6 / 18 |
| X-3 누락 (경계 건 확정 처리) | 0 / 12 | 4 / 10 |
| 처리 정답률 | 75.0% | 62.9% |
| 6칸 모두 정답 | 28.1% | 8.1% |

**분석** — 프롬프트 v2.1의 Critical 보강은 개발용 기준선 오답을 분석해 만들었다. 평가용에서 놓친 Critical 5문항(S04 패배 기록 누락, B20 분쟁 해역 명칭, B15 계정 연동 후 데이터 소실, S11 점검 후 장비 소실, S16 다수 유저 동시 접속 끊김)은 모두 프롬프트에 해당 규칙이 문장으로 들어 있는데도 Critical로 판정되지 않았다. 규칙 문장이 처음 보는 표현으로 일반화되지 않았고, 개발용에서의 개선 일부는 개발용 문항 표현에 맞춘 효과였던 것으로 판단한다. X-3 4건 중 2건(B20)은 개발용 S03과 같은 "결함을 개선 제안으로 분류해 개발 배정" 유형이다.

**v1.4·v1.5 과제**
- 판단 기준을 프롬프트 문장이 아니라 다른 방식으로 전달하는 방법 비교 — 판정 기준서에서 만든 예시(평가셋 문항이 아닌 별도 예시), 분류·우선순위를 나눠 묻는 단계적 판정 등. 효과는 여러 seed로 판정한다 ([KL-002](#kl-002))
- "개선 제안 + 개발 배정"으로 경계 건이 종결되는 경로를 안전장치가 다루지 못하는 문제 검토
- 확신할 수 없는 건(Critical 가능성, 경계 사례)을 사람 검토 큐로 보내는 라우팅으로 위험 건 누락 0건을 지키는 구조 (v1.5)
- 평가용 세트는 이번 측정으로 한 번 사용했다. v1.4에서 같은 세트로 다시 최종 측정하면 v1.3 결과를 보고 고친 영향이 섞이므로, v1.4 최종 측정용 문항을 새로 마련할지 함께 정한다
