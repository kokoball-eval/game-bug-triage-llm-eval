# 버그 리포트 1차 트리아지 판정 안내서 (채점자용)

> 판정 기준서 v1.4를 채점자가 바로 쓸 수 있게 옮긴 문서입니다. 판정 규칙은 기준서와 같고, 기준서에 있던 근거 출처와 평가 문항 번호는 뺐습니다.

## 1. 부탁드리는 일

가상 모바일·PC 게임 **"Aether Raid"**에 들어온 버그 리포트 **63건**을 읽고, 리포트마다 **6개 칸**을 판정해 주시면 됩니다. 실무에서 리포트를 받아 1차 분류하던 그 일입니다.

| 항목 | 내용 |
| :--- | :--- |
| 할 일 | 리포트 63건 × 6칸(분류·모듈·우선순위·재현 정보·발생 빈도·처리)을 판정 시트에서 고르기 |
| 걸리는 시간 | 약 2~3시간. 나눠서 하셔도 됩니다 (저장 후 이어서) |
| 준비물 | 이 안내서, 판정 시트(엑셀) |
| 결과의 쓰임 | 같은 기준으로 다른 QA가 판정했을 때 기존 정답과 얼마나 같은지(라벨 일치율)를 재는 데만 씁니다. 사람을 평가하지 않습니다 |
| 공개 범위 | 결과는 "채점자 1(시니어급 QA)·채점자 2(주니어급 QA)"로만 표기하고, 이름은 공개하지 않습니다 |

**정답을 맞히는 시험이 아닙니다.** 판정이 기존 정답과 다르게 나오면, 그건 채점자의 실수가 아니라 **기준서가 모호하거나 원래 판단이 갈리는 곳**을 찾았다는 뜻입니다. 이 작업으로 얻고 싶은 것이 바로 그 정보입니다. 평소 실무에서 판정하시던 감각대로, 다만 아래 기준서를 따라 판정해 주세요.

## 2. 진행 방법

1. 이 안내서의 **3. 지켜 주실 것**과 **4. 판정 기준**을 한 번 읽습니다 (약 20분).
2. 판정 시트의 **`작성 예시`** 탭에서 예시 2건이 어떻게 채워졌는지 봅니다.
3. **`판정`** 탭에서 Q01부터 순서대로 리포트를 읽고, 노란 칸 6개를 드롭다운에서 고릅니다.
4. 확신이 낮거나 고민한 문항은 **`확신도`**를 "낮음"으로 두고, **`메모`**에 고민한 이유를 한 줄 적습니다. 메모는 기준서를 고칠 때 가장 큰 도움이 됩니다.
5. 63건을 마치면 **`시작하기`** 탭의 진행률이 100%인지 확인하고, 파일을 그대로 보내 주세요.

## 4. 판정 기준

### 4.0 먼저 알아 둘 것

**입력 종류 (트랙)** — 리포트는 두 종류로 들어옵니다. 판정 규칙이 일부 다르니 각 리포트의 `입력 종류`를 먼저 봐 주세요.

| 트랙 | 입력 | 판정의 목적 |
| :--- | :--- | :--- |
| **(A) 커뮤니티 제보 원문** | 유저가 커뮤니티·공식 홈페이지에 쓴 글 | 걸러내기 — 등록할 것, 정보를 더 받을 것, 버릴 것을 가른다 |
| **(B) QA 작성 BTS 이슈** | 내부·퍼블리셔 QA(또는 운영/CS)가 양식대로 쓴 이슈 | 우선순위 제안과 작성 품질 점검 |

**이슈의 흐름** — 트랙 A는 운영/CS가 BTS에 등록하고, 트랙 B는 QA가 등록합니다. 등록된 이슈는 개발 QA가 재현을 확인한 뒤 대응 여부를 정합니다. 이번 판정은 **등록 단계(1차 트리아지)**를 대신하는 일이고, 재현과 대응 결정은 대신하지 않습니다. 그래서 트랙 A에서 등록된 티켓은 "재현 대기" 상태로 들어가고, 트랙 B는 QA가 이미 재현을 확인했으므로 개발팀에 바로 배정합니다.

**Critical은 리드 QA 사인을 거칩니다** — Critical 후보는 개발팀에 직접 보내지 않고, 리드 QA에게 즉시 알려 사인을 받은 뒤 전달합니다. 이것이 `처리: 긴급 사인 요청`입니다.

**리포트 아래의 참고 정보** — 각 리포트에는 `참고: 업데이트 공지`(최근 패치 내용)와 `참고: 기존 등록 이슈`(이미 BTS에 있는 이슈 목록)가 붙어 있습니다. 공지된 조정인지, 이미 등록된 이슈와 같은 현상인지(중복) 판단할 때 씁니다.

### 4.1 분류

| 규칙 | 내용 |
| :--- | :--- |
| C-1 | 기획·명세와 다르게 동작하면 **결함** |
| C-2 | 기획서대로 동작하지만 사용성이 나빠 개선이 필요하면 **개선 제안** |
| C-3 | 플레이 방법 문의, 기능 요청, 운영 문의는 **문의·건의** |
| C-4 | 이미 등록된 이슈(참고: 기존 등록 이슈)와 같은 현상이면 **중복 의심** |
| C-5 | 욕설, 게임과 무관한 글, 결함 정보가 전혀 없는 감정 표출은 **무관** |
| C-6 | 감정적 불만이라도 그 안에 결함 정보가 있으면 결함 부분을 판정한다 |
| C-7 | 기획 의도와 다르지 않고 시스템 오류도 아닌 현상(유저가 찾아낸 공략 등)은 **버그 아님**. 개선 제안과 달리 수정 요청 자체가 아니다 |
| C-8 | **다른 유저의 부정행위 신고**(부계정 승점 몰아주기, 핵 사용, 매크로 등)는 행위자 제재가 목적이면 **문의·건의**(CS 응대). 개발사가 대응할 사항이 아니다. 단, 신고 내용에 **시스템이 막지 못하는 방법**(재현 가능한 악용 절차)이 들어 있으면 그 부분은 **결함** |
| C-8b | 부정행위 신고라도 **시스템 구조의 허점**(예: 저인원 시간대에 같은 길드·부계정끼리 매칭되는 규칙)을 고쳐야 막을 수 있으면 **개선 제안**으로 등록해 개발이 대응하고, 행위자 제재 요청은 운영/CS에 따로 넘긴다. 매크로처럼 제재로 해결되는 신고는 C-8 |
| C-9 | **같은 상황에서 동시에 발생하는 여러 현상**(예: 전화 수신 후 사운드 끊김 + 화면 멈춤)은 하나의 결함으로 판정한다. 우선순위는 가장 심한 현상 기준, 모듈은 두 개까지 고른다 |

### 4.2 모듈

클라이언트 안정성 · 네트워크 · 계정·로그인 · 결제·재화 · 콘텐츠 진행 · 게임플레이·밸런스 · 그래픽·사운드 · UI·텍스트 · 플랫폼 호환성 · 보안·어뷰징

- 가장 관련 있는 모듈 하나를 `모듈1`에 고릅니다. 두 모듈이 함께 걸리면(C-9 등) `모듈2`에 하나 더 고릅니다. 하나면 `모듈2`는 비워 둡니다.
- 결함 정보가 없는 글(무관, 순수 문의 등)은 `모듈1`에 **해당 없음**을 고릅니다.

### 4.3 우선순위

**기본 기준**

| 등급 | 기준 | 대표 예시 |
| :--- | :--- | :--- |
| **Critical** | 핵심 진행을 완전히 차단하거나 유저 데이터·매출에 치명적. 우회 방법 없음. 출시 전이면 빌드를 멈추고 수정, 라이브면 즉시 핫픽스 | 실행 불가·100% 크래시, 결제 후 재화 미지급 또는 무한 획득, 세이브 데이터 소실·로그인 불가, 메인 퀘스트 진행 불가 |
| **Major** | 핵심 기능·플레이 경험에 큰 지장이 있으나 구동은 되거나 우회 가능. 다음 정기 업데이트 전까지 반드시 수정 | 핵심 스킬 데미지 미적용, 구형 기기 심한 프레임 저하, 서브 퀘스트 완료 불가, 상점 UI가 깨져 가격 식별 곤란 (특정 해상도에서만 겹치면 Minor) |
| **Minor** | 코어 루프는 정상이나 UX를 해치거나 부가 기능이 의도와 다름. 여유 있을 때 수정, Known Issue로 출시 가능 | 텍스트 오버플로, 효과음 지연, 가벼운 클리핑, 업적 아이콘 오출력 |
| **Trivial** | 플레이 지장 없음. 대부분 눈치채지 못하는 미관상 결함. Won't fix 가능 | 단순 오타·띄어쓰기, 버튼 1~2px 어긋남, 극도로 특이한 조작에서만 나는 시각 오류, 배경 소품 그림자 누락 |
| **판단보류** | 결함으로 보이지만 우선순위를 정할 정보가 부족 | |
| **해당 없음** | 분류가 결함·개선 제안·중복 의심이 아님 | |

- 결함·개선 제안은 우선순위를 매깁니다. 중복 의심은 **기존 이슈의 우선순위**를 따릅니다. 그 밖의 분류(버그 아님·문의·건의·무관)는 **해당 없음**입니다.
- Minor와 Trivial은 둘 다 "여유 있을 때 수정" 대상이라 서로 바뀌어도 처리 차이가 작습니다. 가장 중요한 경계는 **결함인지 아닌지**, 그리고 **Critical인지 아닌지**입니다.

**발생 빈도에 따른 조정**

- 빈도는 대략적인 재현 빈도로 봅니다. **항상·간헐적**이면 Critical 현상은 Critical을 유지합니다(간헐적도 "생각보다 꽤 자주"라는 뜻).
- **1회**면 일시적 현상일 수 있어 Major~Minor까지 열어 두되, 크래시처럼 심각한 현상은 Major입니다.
- **예외:** 결제·재화 피해, 데이터 소실·롤백, 다수 유저 서버 장애는 사건이 한 번이어도 피해가 남으므로 Critical을 유지합니다.
- **예외의 단서:** 보유 한도 도달처럼 **드문 조건에서만 생기고 우회 경로가 있는 무료 보상 손실**은 Major까지 낮출 수 있습니다(DB 보정으로 복구 가능). 유료 재화 손실이면 Critical입니다.

**경계 규칙 — 실무에서 부서마다 판정이 갈리는 상황**

아래 상황은 원래 판단이 갈립니다. 그래서 정답 범위를 넓게 두고, `처리`는 반드시 **사람이 확인하는 쪽**(긴급 사인 요청 / 등록(재현 대기) / 정보 요청 후 보류)으로 보냅니다(H-8). 개발 QA가 재현으로 상황을 파악하는 것도 사람 확인으로 봅니다.

| 규칙 | 상황 | 분류 | 우선순위 | 처리 | 판단이 갈리는 이유 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| P-B1 | 기술적으로는 경미하지만 **조롱거리가 될 만한 시각 결함** (컷신 안면 텍스처 소실 등) | 결함 | Major (경우에 따라 Minor). Critical까지는 아님 | 등록(재현 대기) | 기술 기준은 Minor, 사업부는 마케팅 타격으로 Critical |
| P-B2 | **민감한 텍스트 오류** (분쟁 지역 명칭 오기, 필터를 우회한 욕설이 된 오타) | 결함 | Critical | 긴급 사인 요청 | 단순 오타면 Trivial이지만 사회적·법적 파장 |
| P-B3 | **점유율이 극히 낮은 구형·특정 기기의 확정 크래시** | 결함 | Critical | 긴급 사인 요청 | 크래시 자체는 Critical, 개발팀은 리소스 대비 효율로 Minor·Won't fix 주장 |
| P-B4 | **지형지물을 이용한 공략** (AI가 인식하지 못하는 위치에서 일방적 사냥) | 결함 (버그 아님도 가능) | Major (직업 밸런스와도 연관) | 등록(재현 대기) — 개발 QA 재현·어뷰징 테스트 먼저 | 기획은 밸런스 붕괴, QA는 시스템 오류 아님. 수정 시 유저 반발 위험 |
| P-B5 | **기획서대로지만 UX가 최악** (일괄 판매 없음 등 반복 조작 강요) | 개선 제안 | Trivial | 개발 배정 — 개선 제안은 일단 바로 넘기고, 판단은 기획·개발 몫 | QA는 이탈 우려로 Major, 개발은 기획서대로라 Not a Bug |
| P-B6 | **"패치 후 능력치·수치가 줄었다"** 제보 | 아래 순서를 따름 | 아래 순서를 따름 | 아래 순서를 따름 | 대부분 기간제 효과 만료나 공지된 조정이지만, 드물게 밸런스 작업 중 테이블 데이터 실수가 있고 그 경우 핫픽스급 |

**P-B6 처리 순서**

1. 기간제 효과(이벤트 컬렉션·장비) 만료 시점과 겹치면 → 버그 아님 가능성이 높지만, 개발 QA의 재현 확인(문제 상황 파악)이 먼저이므로 **등록(재현 대기)**. 확인되면 CS 응대(만료 안내)
2. 공지(패치 노트)의 조정 내용과 일치하면 → 1과 같이 **등록(재현 대기)** 후 CS 응대
3. **공지된 수치와 실제 수치가 다르거나**, 공지 없이 바뀌었으면 → 결함 가능성. 테이블 데이터 대조 후 인게임 테스트를 권장. **Critical, 긴급 사인 요청** (테이블 실수로 확인되면 핫픽스)
4. 리포트만으로 1~3을 가릴 수 없으면 → **판단보류 + 정보 요청 후 보류** (어떤 능력치가, 언제부터, 기간제 아이템 착용 여부를 요청)

### 4.4 재현 정보

"재현에 성공했는가"가 아니라 **"재현을 시도할 정보가 있는가"**를 봅니다.

| 규칙 | 내용 |
| :--- | :--- |
| R-1 | 트랙 B는 양식의 `[테스트 환경]`(플랫폼·빌드 버전), `[재현율]`, `[이슈 설명]`, `[실제 결과]`가 채워져 있으면 **충분** |
| R-2 | 트랙 A는 플랫폼·기기, 발생 상황(어디서 무엇을 할 때)이 있으면 **충분**. 빌드 버전은 유저가 모르는 경우가 많으므로 필수로 보지 않음 |
| R-3 | 재현을 시도할 수 없을 만큼 정보가 부족하면 **부족** |
| R-4 | 기기 특정 이슈가 많으므로(해상도·UI 스케일·접속), 기기 모델이 없으면 누락 정보로 먼저 요청 |
| R-5 | 트랙 A의 빌드는 게시 일시와 업데이트 일정으로 추정하므로, 빌드 버전이 없다는 이유로 부족으로 보지 않음 |

### 4.5 발생 빈도

리포트에 **적힌** 빈도만 옮기고 추론하지 않습니다.

| 고를 값 | 리포트에 이렇게 적혀 있으면 |
| :--- | :--- |
| **항상** | 매번·무조건·100%·"세 번 다"·재현율 10/10 |
| **간헐적** | 계속·여러 번·"오늘만 세 번째"처럼 반복은 말했지만 매번인지 모를 때 |
| **1회** | 한 번 일어난 사건 (결제 1건, 점검 후 데이터 소실) |
| **미기재** | 빈도가 적혀 있지 않음. 조건문("~하면 ~됨"), 플랫폼 범위("아이폰이든 PC든 똑같음"), 방법 설명도 미기재. 부정행위 신고처럼 현상은 있는데 빈도가 없어도 미기재 |
| **해당 없음** | 결함 현상을 다루지 않는 글 (무관, 개선 제안, 순수 문의·건의) |

- 트랙 B에서 `[재현율]` 칸이 비어 있으면 R-1을 충족하지 못한 것이므로 작성자에게 보완을 요청합니다(H-7).

### 4.6 처리

**기본 규칙**

| 규칙 | 내용 |
| :--- | :--- |
| H-1 | 우선순위가 **Critical 후보**면 재현 전이라도 **긴급 사인 요청** |
| H-1b | **여러 유저가 동시에 겪는 서버 쪽 장애 의심**(정해진 시간의 길드전에서 한 길드 전원 동시 끊김 등)은 개발 QA가 재현할 수 없고 서비스 신뢰성 문제이므로, 기기 정보가 없어도 **Critical, 긴급 사인 요청**. 단일 유저의 크래시·로그인 불가(H-3a)와 구분 |
| H-2 | 트랙 A: 결함·개선 제안이고 재현 정보가 충분하면 **등록(재현 대기)** (개선 제안은 H-2d가 우선) |
| H-2b | 트랙 B: QA가 재현까지 확인해 쓴 이슈(R-1 충족)는 Critical이 아니면 **개발 배정**. Critical이면 H-1의 긴급 사인 요청 |
| H-2c | 트랙 B라도 **운영/CS가 유저 항의를 옮겨 적은 이슈**는 QA 재현 전이므로 **등록(재현 대기)**이 기본. 정보가 확실하면 개발 배정도 가능 |
| H-2d | **개선 제안은 재현이 필요 없으므로 트랙과 관계없이 개발 배정** |
| H-3 | 결함으로 보이지만 재현 정보가 부족하면 **정보 요청 후 보류** |
| H-3a | 정보가 부족해도 **Critical 가능성이 있는 현상**(크래시, 로그인 불가, 결제, 데이터 소실)이면 긴급 사인 요청하지 않고 **정보 요청 후 보류**. 우선순위는 **판단보류**. 동시에 개발 QA의 재현 확인을 권장 |
| H-4 | 분류가 무관이면 **폐기**. 대리충전·불법 거래 광고도 개발사가 대응할 사항이 아니므로 폐기 |
| H-5 | 분류가 중복 의심이면 **폐기** (기존 이슈에 없는 새 정보가 있으면 기존 이슈에 덧붙이도록 권장) |
| H-6 | 문의·건의는 BTS에 올리지 않고 **CS 응대** |
| H-6b | 버그 아님은 **폐기**. 단, 유저 반발이 예상되는 경우(P-B4 등)는 사람 확인 처리로 보냄 |
| H-7 | 트랙 B에서 R-1의 필수 칸이 비어 있으면 **정보 요청 후 보류** (작성자에게 보완 요청) |

**사람 확인 규칙**

| 규칙 | 내용 |
| :--- | :--- |
| H-8 | 4.3의 경계 규칙(P-B1~B6)에 해당하면 사람이 확인하는 처리(**긴급 사인 요청**, **등록(재현 대기)**, **정보 요청 후 보류**)로만 보낸다. P-B5(개선 제안)는 개발 배정 |
| H-9 | **결함일 가능성이 있는 제보는 폐기하지 않는다.** 확신이 없으면 폐기보다 보류 |
| H-10 | **유저가 직접 검증할 수 없는 수치 의혹**(확률 조작, 보스 난이도가 버그 같다 등)은 CS 안내나 폐기로 끝내지 않고 **등록(재현 대기)**로 보내, 개발 QA가 데이터 테이블·확률 검증 툴 대조 또는 밸런스 재테스트로 먼저 판단한다. 근거 없이 Critical로 올리지도 않는다 |

## 5. 판정 예시

평가 문항과 겹치지 않게 따로 만든 리포트입니다. 판정 시트의 `작성 예시` 탭에도 같은 내용이 있습니다.

**예시 1 — 정보가 부족한 단문 제보**

```text
[입력 종류] (A) 커뮤니티 제보 원문
[게시판] 자유게시판
[게시 일시] 2026-08-05 22:41
[제목] 낚시하면 멈춤
[본문]
낚시만 하면 화면 멈춰요
```

| 분류 | 모듈1 | 우선순위 | 재현 정보 | 발생 빈도 | 처리 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 결함 | 클라이언트 안정성 | 판단보류 | 부족 | 미기재 | 정보 요청 후 보류 |

판단: 기기·장소가 없어 재현 정보 부족(R-3). 멈춤은 진행 불가일 수 있는 Critical 가능 현상이지만 정보가 부족하므로 판단보류 + 정보 요청 후 보류(H-3a). "~하면 ~됨" 조건문이라 빈도는 미기재.

**예시 2 — QA가 쓴 미관 결함**

```text
[입력 종류] (B) QA 작성 BTS 이슈
[작성자] 내부 QA
[제목] [UI] 우편함 닫기 버튼 아이콘이 2px 왼쪽으로 어긋남
[본문]
[테스트 환경] PC / 빌드 2.3.0.1544 (QA 빌드)
[재현율] 10/10 (100%)
[이슈 설명] 우편함 창 오른쪽 위 닫기(X) 버튼의 아이콘이 버튼 영역 중앙에서 왼쪽으로 2px 치우쳐 표시됨. 버튼 입력은 정상.
[기대 결과] 아이콘이 버튼 영역 중앙에 표시된다.
[실제 결과] 아이콘이 왼쪽으로 2px 치우침. 클릭·터치 영역은 정상.
```

| 분류 | 모듈1 | 우선순위 | 재현 정보 | 발생 빈도 | 처리 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 결함 | UI·텍스트 | Trivial | 충분 | 항상 | 개발 배정 |

판단: 1~2px 어긋남, 플레이 지장 없음 → Trivial. 양식이 다 채워져 있어 충분(R-1). 10/10 → 항상. 트랙 B이고 Critical이 아니므로 개발 배정(H-2b).

## 6. 자주 묻는 질문

**Q. 리포트 하나에 결함이 여러 개 섞여 있으면?**
같은 상황에서 함께 일어나는 현상이면 하나의 결함으로 보고 가장 심한 현상 기준으로 판정합니다(C-9). 서로 관계없는 결함이 섞여 있으면, 가장 심한 결함을 기준으로 판정하고 메모에 "복합"이라고 적어 주세요.

**Q. 두 값 사이에서 정말 모르겠으면?**
기준서에 가장 가까운 값을 하나 고르고, 확신도를 "낮음"으로, 메모에 두 후보를 적어 주세요 (예: "Major/Minor 고민 — 우회 가능 여부 불명확").

**Q. 실무 감각과 기준서가 다르면?**
기준서를 따라 판정하고, 메모에 실무에서는 어떻게 판정했을지를 적어 주세요. 기준서를 고칠 때 가장 중요한 자료가 됩니다.

**Q. 시간이 얼마나 걸려야 정상인가요?**
한 건에 2~3분이면 충분합니다. 오래 고민되는 건은 메모를 남기고 넘어가셔도 됩니다.
