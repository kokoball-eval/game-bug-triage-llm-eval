# v1.3 최종 측정 보고서 — 평가용 세트

> 측정일 2026-10-02 · 실행 기록 `data/results/v13/history/v13_test_20261002_161508.json` · 채점 결과 `data/results/v13/score_v13_test_20261002_161508.json`
> 자동 생성된 채점 요약표는 [`eval_v13.md`](eval_v13.md)에 있다. 이 문서는 그 결과를 개발용 결과와 비교하고 원인을 정리한 것이다.
> 본문의 [ML]·[PE]·[LC] 표기는 KANT AI 부트캠프 Private LLM 트랙 과정 기록(TIL) 링크다. ML은 머신러닝, PE는 프롬프트 엔지니어링, LC는 LangChain 과정이며 뒤의 숫자는 학습일이다.

## 요약

- **무엇을 했나** — 개발 과정에서 한 번도 쓰지 않은 리포트 31건(평가용 세트)으로 v1.3 최종 구성을 한 번 측정했다.
- **결과** — 코드로 강제한 규칙(정해진 값만 쓰기, 한국어로만 쓰기, 결함 제보를 버리지 않기)은 처음 보는 리포트에서도 **모두 지켜졌다**. 반면 모델이 스스로 판단해야 하는 부분(얼마나 심각한지, Critical인지)은 개발용 세트보다 **눈에 띄게 떨어졌다**.
- **의미** — 코드가 보장하는 부분은 믿을 수 있지만, 모델 판단에 맡긴 부분은 아직 사람이 확인해야 한다. 판단 정확도를 높이는 방법은 v1.4에서, 위험한 건을 사람에게 넘기는 구조는 v1.5에서 다룬다.
- **설계 기준** — 측정 절차와 출력 검증은 LLM 트랙에서 학습한 평가 설계·출력 복구 원칙을, 처리 규칙과 위험도 판단은 게임 개발 QA의 트리아지 실무 기준을 따랐다. 적용한 원칙은 8절에 모았다.

## 1. 이 측정을 하는 이유

평가셋 63건은 처음부터 두 묶음으로 나눠 두었다.

| 묶음 | 건수 | 쓰임 |
| :--- | :---: | :--- |
| 개발용(dev) | 32건 | 프롬프트와 안전장치를 고칠 때 결과를 보며 반복 측정 |
| 평가용(test) | 31건 | 개발이 끝난 뒤 **한 번만** 측정 |

개발용 세트는 결과를 보면서 고쳤기 때문에 점수가 잘 나오는 것이 당연하다. 시험으로 비유하면 개발용은 오답 노트를 만들며 반복해서 푼 연습 문제이고, 평가용은 처음 보는 시험지다. 처음 보는 리포트에서도 같은 수준이 나와야 실제 운영에서 믿을 수 있다.

이 구성은 머신러닝 과정의 데이터 분리와 "Test 세트를 봉인해 두고 모든 선택이 끝난 뒤 1회만 평가한다"는 원칙([ML 08/11][ml0811], [ML 08/14][ml0814], [ML 08/18][ml0818])과, 프롬프트 엔지니어링 과정의 "개발 데이터로 프롬프트를 고르고 고정한 뒤 최종 평가는 한 번만 실행한다"는 평가 절차([PE 10/02][pe1002])를 따른 것이다. 과정 실습의 `RUN_FINAL` 플래그처럼, 평가용 세트는 `--final`을 명시해야만 실행되도록 코드로 막았다. QA 실무로 보면 릴리스 판정에 쓰는 테스트 케이스를 판정 전에 동결하는 것과 같다.

그래서 결과를 보기 전에 규칙을 먼저 고정한다는 원칙([ML 08/18][ml0818]의 사전 선정 규칙)에 따라, 측정 전에 **"결과가 어떻게 나오든 그대로 기록하고, 결과를 보고 프롬프트·안전장치·채점기를 고치지 않는다"**고 정했다. 평가용 결과를 보고 고치기 시작하면 평가용 세트도 연습 문제가 되어 버린다. 과정에서 강조한 "결과를 골라 남기지 않고, 개선이 없어도 그대로 기록한다"는 원칙([PE 10/02][pe1002])이다.

측정 환경도 함께 통제했다. 같은 seed라도 실행 환경이 다르면 결과가 달라진다는 환경 재현성 원칙([LC 09/29][lc0929])에 따라, 측정 전에 GPU 점유와 전원 연결을 점검하고(`--strict-env`), Ollama에 남은 이전 상태를 비우는 `ollama stop`을 측정 절차에 넣었다([OBS-002](../docs/issue_log.md#obs-002)).

## 2. 이 보고서에 나오는 용어

| 용어 | 뜻 |
| :--- | :--- |
| 응답 수 | 문항마다 2번씩 실행하므로 평가용 31건 → 62응답, 개발용 32건 → 64응답 |
| 허용 값 위반 | 분류·우선순위 등에 정해진 선택지 밖의 값(예: '무관 중')을 쓴 응답 |
| 출력 언어 위반 | 응답에 한국어가 아닌 문자(예: 한자)가 섞인 응답 |
| 형식 STRICT | 8개 칸이 순서대로 빠짐없이, 정해진 형식으로 나온 응답의 비율 |
| X-1 누락 | **Critical 결함을 리드 QA에게 올리지 않은 응답** — 가장 위험한 실수 |
| X-2 누락 | **결함 제보를 폐기한 응답** — 아무도 다시 보지 않게 되는 실수 |
| X-3 누락 | 부서마다 판단이 갈려 **사람이 확인해야 하는 건을 바로 종결한 응답** |
| 과잉 상신 | Critical이 아닌 건을 Critical로 올린 응답 (리드 QA 업무가 늘어남) |
| 6칸 모두 정답 | 분류·모듈·우선순위·재현 정보·발생 빈도·처리 6칸이 모두 맞은 응답 |
| 모델 원본 / 최종 출력 | 모델이 처음 낸 답 / 형식 재요청·폐기 확인·후처리 안전장치를 거쳐 실제로 BTS에 들어가는 답 |

X-1 누락과 과잉 상신을 정답률과 따로 세는 것은 평가지표 선택 원칙([ML 08/11][ml0811])에 따른 것이다. Critical은 전체 응답의 일부여서 정답률 하나로 묶으면 놓친 Critical이 드러나지 않는다. X-1 누락은 재현율, 과잉 상신은 오탐에 해당한다. 트리아지 실무에서도 두 실수의 비용은 다르다. Critical 누락은 라이브 서비스의 장애 대응을 늦추고, 과잉 상신은 리드 QA의 검토 시간을 쓴다. 그래서 X-1 누락을 가장 무거운 실수로 둔다.

## 3. 결과 — 두 묶음으로 나눠 본다 (qwen2.5:7b)

## 4. 왜 판단 항목만 떨어졌나

### 4.1 개발용 문항에 맞춰진 효과

v1.3 초반에 개발용 기준선에서 Critical을 놓친 문항들을 분석해서, 프롬프트에 "이런 유형도 Critical이다"라는 규칙 문장을 추가했다. 그 결과 개발용에서는 X-1 누락이 13건에서 2건으로 줄었다.

그런데 평가용에서 놓친 Critical 5문항을 보면, **해당 규칙이 프롬프트에 이미 문장으로 들어 있었다.** 같은 유형이라도 표현이 다르자 모델이 규칙을 적용하지 못한 것이다.

| 문항 | 리포트 내용 | 프롬프트에 있던 규칙 | 모델 판단 |
| :--- | :--- | :--- | :--- |
| S04 | 지기 직전 강제 종료하면 패배 기록이 안 남음 | "승패·랭킹 기록이 남지 않는 결함" | Major |
| B20 | 지도의 동해가 '일본해'로 표기됨 | "분쟁 지역 명칭 같은 민감한 텍스트 오류" | Minor (개선 제안) |
| B15 | 계정 연동 후 캐릭터·결제 패키지가 사라짐 | "데이터 소실·롤백" | Major |
| S11 | 점검 후 +12 강화 장비가 사라짐 | "데이터 소실·롤백" | Minor (버그 아님) |
| S16 | 길드전 종료 직전 길드원 전원이 동시에 튕김 | "여러 유저가 동시에 겪는 서버 장애" | Major |

연습 문제의 오답 노트를 외워서 연습 문제는 맞혔지만, 표현이 바뀐 시험 문제에는 그 지식을 적용하지 못한 것과 같다. 7B 모델에게 프롬프트 문장으로 판단 기준을 가르치는 방식에는 한계가 있다는 결론이다([KL-003](../docs/issue_log.md#kl-003)).

머신러닝 과정에서 Test 세트를 봉인하는 이유로 다룬 내용([ML 08/14][ml0814], [ML 08/18][ml0818])이 그대로 드러난 결과다. 개발 데이터의 결과를 보며 반복해서 고르면 그 데이터의 점수는 실제 성능보다 좋게 나온다. 평가용 세트를 따로 두지 않았다면 개발용 점수만 보고 판단 정확도가 충분하다고 잘못 결론 냈을 것이다. 테스트 실무의 살충제 역설, 즉 같은 테스트만 반복하면 새로운 유형의 결함을 찾지 못한다는 원칙과도 통한다.

### 4.2 사람이 확인해야 할 건을 바로 종결한 4건 (X-3)

| 문항 | 리포트 내용 | 모델이 한 일 | 문제 |
| :--- | :--- | :--- | :--- |
| B20 (2회 모두) | 지도 해역 명칭 오표기 | 결함이 아니라 "개선 제안"으로 분류하고 개발팀에 바로 배정 | Critical 결함인데 리드 QA를 거치지 않았다. 개발용에서도 같은 방식의 실패(S03)가 있었다 |
| S07 | 의상 버그로 캐릭터 얼굴이 늘어나 조롱거리가 됨 | "버그 아님"으로 보고 CS 응대로 종결 | 사람이 확인해야 할 시각 결함을 종결했다 |
| S10b | 패치 후 공격력이 갑자기 떨어졌다는 제보 | "버그 아님"으로 보고 CS 응대로 종결 | 데이터 확인이 필요한 건을 종결했다 |

후처리 안전장치는 모델이 "결함"으로 분류한 경우에만 처리 규칙을 바로잡는다. 그래서 분류 자체를 "개선 제안"이나 "버그 아님"으로 잘못 판단하면 막지 못한다.

트리아지 실무에서 판단이 갈리는 건을 담당자 혼자 종결하지 않고 리드 확인을 거치게 하는 이유가 이것이다. 분류를 잘못하면 그 뒤의 처리 규칙이 모두 엇나간다. 프롬프트 엔지니어링 과정에서는 이렇게 자동으로 처리할 수 없는 건을 사람 검토 큐로 격리하는 방식을 다뤘다([PE 09/11][pe0911] 7-3강). 이를 v1.5 과제로 둔다(9절).

### 4.3 그 밖에 자주 틀린 유형

- **결함이 아닌 글에 심각도를 붙임** — 제재 요청이나 가챠 결과 공유처럼 우선순위가 "해당 없음"이어야 하는 응답 16건 중 15건이 틀렸다.
- **분류 혼동** — 다른 유저 제재 요청(B16)과 이미 등록된 이슈의 중복(B18)을 새 결함으로 봤다. 반대로 실제 결함 4문항(A02, B08, S07, S11)은 "버그 아님"으로 봤다.
- **QA가 작성한 이슈(트랙 B)에서 처리 정답률이 가장 낮음** — 20응답 중 9건(45%)만 맞았다. QA가 작성한 이슈는 재현 절차가 갖춰져 있어 커뮤니티 제보와 처리 경로가 다르다. 판정 기준서가 입력 종류와 작성자에 따라 규칙(H-2, H-2b)을 나눈 것도 이 실무 구분 때문인데, 모델은 이 구분을 안정적으로 따르지 못했다.

## 5. 코드 단계가 실제로 한 일

코드 단계는 과정에서 학습한 출력 검증·복구 흐름을 그대로 따른다.

- **제한된 복구** — 검증에 실패한 칸만 1번 다시 요청하고, 다시 받은 값도 처음과 같은 형식 계약으로 검증한다. 그래도 위반이면 첫 응답을 남긴다. "검증 실패 → 1회 복구 → 같은 Parser로 재검증" 흐름([LC 09/30][lc0930] 5-3강, [PE 09/11][pe0911] 7-3강)이다. 횟수 제한은 비용 상한과 종료 보장을 위한 것이다.
- **허용 목록으로 제한** — 다시 받는 값은 JSON Schema의 허용 값 목록(`enum`)과 허용 문자 패턴(`pattern`)으로 제한한다. 모델이 만든 값을 신뢰할 수 없는 외부 입력으로 다루는 방식([PE 09/11][pe0911] 8-2강)이다.
- **원본 보존** — 실행 기록에 모델 원본 응답, 재요청 시도, 적용된 안전장치 규칙을 함께 남긴다([PE 10/02][pe1002]의 원문 보관 원칙).

복구 로직이 있으면 최종 형식 준수율은 높게 나오지만, 그것이 모델 실력인지 복구 덕분인지는 구분되지 않는다. 그래서 1차 결과와 복구 후 결과를 따로 집계하라는 원칙([LC 09/30][lc0930])에 따라, 같은 평가용 응답을 모델 원본과 최종 출력으로 각각 채점했다.

| 지표 | 모델 원본 | 최종 출력 | 바뀐 이유 |
| :--- | :---: | :---: | :--- |
| 허용 값 위반 | 9건 | 0건 | 형식 재요청 9건이 모두 고쳐짐 |
| 형식 STRICT | 53 / 62 | 62 / 62 | 위와 같음 |
| 처리 정답 | 34 / 62 | 39 / 62 | 형식 재요청과 후처리 안전장치(QA 작성 결함 4건을 개발 배정으로 보정) |
| 6칸 모두 정답 | 4 / 62 | 5 / 62 | — |

폐기 확인 질문은 결함 정보가 없는 욕설 글(A16) 2건에서 "무관"으로 답해 폐기를 유지했다. 코드 단계는 형식과 절차는 확실히 바로잡지만, 모델이 처음부터 잘못 내린 판단(예: Critical을 Major로 본 것)까지 바꾸지는 않는다. 이는 설계 의도이기도 하다. 판단까지 코드가 바꾸면 모델이 틀린 사실이 측정에서 가려지기 때문이다. 잘못된 값을 비슷한 허용 값으로 조용히 바꾸지 않는다는 fail loud 원칙([PE 10/02][pe1002], [LC 10/01][lc1001])과 같다. QA 실무로 보면, 검수 단계가 결함을 대신 고쳐 버리면 결함 발생률이 실제보다 낮게 집계되는 것과 같은 이치다.

## 6. 날조 2건은 탐지기의 오판으로 판단한다

S17 리포트에는 "100번 뽑았는데", "100연 돌렸는데"라고 적혀 있고, 모델은 요약에 "100회 돌렸으나"라고 썼다. 같은 숫자를 다른 단위 말로 옮겼을 뿐인데, 날조 탐지기가 리포트에 "100회"라는 글자가 없다는 이유로 지어낸 수치로 판정했다.

1절에서 정한 규칙에 따라 탐지기를 지금 고치지 않고 측정값 2건을 그대로 기록한다. 탐지기 수정은 v1.4에서 회귀 테스트와 함께 진행한다([ISSUE-008](../docs/issue_log.md#issue-008)).

테스트 실무에서도 테스트 도구의 오판은 도구 결함으로 따로 등록하고, 이미 끝난 회차의 결과를 고쳐 쓰지 않는다. 고칠 때는 같은 수량을 다른 단위로 옮긴 표현은 통과시키고, 다른 수량은 계속 날조로 잡는지 확인하는 회귀 테스트를 함께 둔다. 오판으로 보이는 결과를 지우지 않고 남긴 것은 결과를 골라 남기지 않는다는 원칙([PE 10/02][pe1002])에 따른 것이다.

## 7. 대조군 (llama3.1:8b)

대조군은 같은 실행에서 같은 평가셋·생성 옵션·seed로 돌려, 모델 외의 조건을 고정했다. 조건 하나만 바꿔 비교한다는 변수 통제 원칙([PE 09/11][pe0911] 6-1강, [PE 10/02][pe1002])이다.

| 지표 | qwen2.5:7b | llama3.1:8b |
| :--- | :---: | :---: |
| 형식 STRICT | 100% | 50.0% |
| 허용 값 위반 | 0건 | 17건 |
| X-1 누락 | 6 / 18 | 18 / 18 |
| 처리 정답률 | 62.9% | 30.6% |
| 평균 응답 시간 | 1.67초 | 3.45초 |

Llama는 칸 자체를 빠뜨린 응답이 많아 형식 재요청으로도 거의 회복되지 않았고(18건 중 1건), Critical을 한 건도 알아보지 못했다. 평가용 세트에서도 Qwen을 선정한 판단은 그대로 유지된다.

## 9. 결론과 다음 과제

1. **코드로 강제한 규칙은 처음 보는 리포트에서도 지켜졌다.** "모델은 판단하고, 형식과 절차는 코드가 강제한다"는 v1.3의 설계가 실제로 통한다는 근거다.
2. **모델의 판단은 개발용 세트에 맞춰져 있었다.** 프롬프트에 규칙 문장을 더하는 방식은 처음 보는 표현에 잘 적용되지 않았다. v1.4에서는 판단 기준을 다른 방식으로 전달하는 방법(기준서에서 만든 별도 예시, 단계를 나눠 묻는 방식 등)을 비교하고, 효과는 seed 여러 개로 판정한다.
3. **지금 구조만으로는 위험 건 누락 0건을 지킬 수 없다.** Critical 가능성이 있거나 판단이 갈리는 건을 사람 검토 큐로 보내는 구조를 v1.5에서 만든다. 자동화가 판단을 대신하는 것이 아니라, 사람이 봐야 할 건을 빠짐없이 골라 넘기는 것이 1차 트리아지의 목표다.
4. **평가용 세트는 이번에 한 번 사용했다.** v1.4의 최종 측정에 같은 세트를 다시 쓰면 이번 결과를 보고 고친 영향이 섞이므로, 새 평가 문항을 마련할지 함께 정한다. 31건은 작은 표본이므로 이번 수치를 모델 전체 성능의 증거로 보지 않는다([PE 10/02][pe1002]의 표본 한계 원칙).
