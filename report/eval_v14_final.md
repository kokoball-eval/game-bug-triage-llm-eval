## 요약

- **풀려는 문제** — v1.3에서 모델은 "이런 경우는 Critical이다"라는 규칙을 프롬프트에서 읽고도, 처음 보는 리포트에는 그 규칙을 적용하지 못했다. 판단 기준을 다른 방식으로 알려 주면 Critical을 덜 놓치는지 확인했다.
- **방법** — 신입 트리아지 담당자를 교육하는 방법 두 가지를 비교했다. 모범 답안을 보여 주는 방법(M1: 판정 예시)과 Critical 체크리스트를 쥐여 주는 방법(M2)이다. 어느 방법을 채택할지는 측정 전에 정해 커밋했다.
- **결정** — **qwen2.5:7b + M2(Critical 체크리스트)**. 개발용에서 Critical 누락이 25건에서 17건으로 줄었고, 다른 지표는 나빠지지 않았다.
- **최종 측정** — 한 번도 실행하지 않은 25건에서 날조·결함 폐기·사람 확인 누락·형식 위반이 모두 0건이었다. Critical 누락은 2/10(한 문항을 2회 모두 놓침)이다. 다만 체크리스트가 이 25건에서 판정을 바꾼 건은 0건이어서, **M2의 효과는 최종 세트에서 확인되지 않았다.**
- **주요 발견** — 더 큰 모델(gemma4:12b)에 체크리스트를 붙이면 개발용에서 Critical을 하나도 놓치지 않았다. 그러나 잘 처리하던 이슈를 다른 곳으로 보내기 시작해 미리 정한 기준을 넘지 못했다. 기준은 결과를 본 뒤 바꾸지 않았고, 이 결과는 v1.5(사람 검토 큐)의 근거로 남긴다.
- **설계 기준** — 실험 절차와 판정 방식은 LLM 트랙에서 학습한 평가 설계 원칙을, 무엇이 Critical이고 어떤 실수가 더 위험한지는 게임 개발 QA 8년의 트리아지 실무 기준을 따랐다. 두 가지가 어디에 쓰였는지는 9절에 모았다.

## 1. 이 보고서에 나오는 말

| 용어 | 뜻 | QA 실무로 비유하면 |
| :--- | :--- | :--- |
| 트리아지 | 들어온 버그 리포트를 분류하고, 심각도를 매기고, 어디로 보낼지 정하는 1차 판정 | 리포트 담당 QA의 일일 업무 |
| Critical | 진행 불가, 결제·데이터 피해처럼 즉시 핫픽스가 필요한 결함 | 라이브 장애 등급 |
| 긴급 사인 요청 | Critical 후보를 리드 QA 사인을 받아 개발팀에 넘기는 처리 | 리드 QA 확인 후 핫픽스 요청 |
| **X-1 누락** | Critical을 리드 QA에게 올리지 않은 응답 — **가장 위험한 실수** | 장애 보고 누락 |
| X-2 누락 | 결함 제보를 폐기한 응답 | 유효한 버그를 "버그 아님"으로 닫음 |
| X-3 누락 | 부서마다 판정이 갈려 사람이 봐야 하는 건을 바로 종결한 응답 | 리드 확인 없이 담당자 혼자 종결 |
| 과잉 상신 | Critical이 아닌 건을 Critical로 올린 응답 | 리드 QA 사인 큐를 불필요하게 채움 |
| 문항 단위 회귀 | 기준에서 맞히던 응답이 후보에서 틀리게 바뀐 수 | 이전 빌드에서 통과하던 케이스가 새 빌드에서 실패 |
| 개발용 / 최종 평가용 | 방법을 고르며 반복 측정하는 문항 / 고르고 난 뒤 한 번만 측정하는 문항 | 연습 문제 / 처음 보는 시험지 |
| seed | 모델의 무작위성을 고정하는 번호. 같은 번호면 같은 답이 나온다. 번호 3개(1·11·21)로 반복해 운으로 나온 결과를 거른다 | 같은 테스트를 여러 번 돌려 우연히 통과한 것인지 확인하기 |

X-1 누락과 과잉 상신을 정답률과 따로 세는 이유가 있다. 둘은 피해의 크기가 다르다. Critical 누락은 라이브 서비스의 장애 대응을 늦추고, 과잉 상신은 리드 QA의 검토 시간을 쓴다. 정답률 하나로 묶으면 이 차이가 사라진다. 평가지표를 오류의 비용에 맞춰 고른다는 원칙([ML 08/11][ml0811])을 트리아지 실무의 장애 등급 기준에 그대로 적용했다.

## 2. 출발점 — v1.3에서 무엇이 문제였나

v1.3 최종 측정([`eval_v13_final.md`](eval_v13_final.md))에서 코드로 강제한 형식·절차(정해진 값만 쓰기, 결함 제보 버리지 않기)는 처음 보는 리포트에서도 지켜졌다. 반면 모델이 스스로 판단해야 하는 Critical 인식은 크게 떨어졌다. 평가용에서 놓친 Critical 5문항은 모두 해당 규칙이 프롬프트에 문장으로 들어 있었다([KL-003](../docs/issue_log.md#kl-003)).

신입 QA에게 심각도 기준표를 외우게 하는 것만으로는 처음 보는 이슈에 기준을 대입하지 못하는 것과 같다. 실무에서는 이럴 때 두 가지 방법으로 교육한다. 과거 판정 사례를 보여 주거나, 판정할 때 확인할 항목을 체크리스트로 준다. 프롬프트 엔지니어링 과정에서도 같은 두 갈래를 다뤘다. 오분류가 잦은 경계 사례를 겨냥한 예시(few-shot)와, 긴 추론 대신 검증 가능한 체크리스트 중심으로 답하게 하는 방식이다([PE 09/11][pe0911] 6-1·6-2강, [PE 10/02][pe1002] 실습 4).

| 방법 | 신입 교육으로 비유하면 | 실제로 하는 일 |
| :---: | :--- | :--- |
| M0 | 지금 그대로 | 프롬프트 v2.3 + 형식 재요청 + 폐기 확인 + 후처리 안전장치 |
| M1 | 모범 답안 4개를 보여 주고 일 시키기 | 프롬프트에 판정 예시 4개(해당 없음·판단보류·Trivial·Critical)를 붙임 |
| M2 | Critical 체크리스트를 쥐여 주기 | 1차 판정 뒤 "결제 피해가 있는가", "반복 악용이 가능한가" 같은 예/아니오 질문 6개를 다시 묻고, 하나라도 "예"면 코드가 Critical로 **올리기만** 함 |

M2를 "올리기만" 하게 한 것도 실무 판단이다. Critical을 놓치면 장애로 이어지고, 잘못 올리면 리드 QA가 한 번 더 보면 된다. 손해가 비대칭이므로 체크리스트는 내리는 쪽으로는 쓰지 않았다.

## 3. 공정하게 비교하기 위해 측정 전에 고정한 것

### 3.1 한 번에 하나씩만 바꿨다

모델과 방법을 함께 바꾸면 결과가 좋아져도 무엇 덕분인지 알 수 없다. 그래서 순서를 나눴다. 같은 모델·데이터·채점 기준에서 한 가지만 바꿔 비교하는 통제 실험이다([PE 09/11][pe0911] 6-1강, [PE 10/02][pe1002]의 비교 쌍 분리). 결함을 재현할 때 조건을 하나씩 바꿔 원인을 좁히는 QA의 방식과 같다.

| 순서 | 바꾼 것 | 고정한 것 | 결과 |
| :---: | :--- | :--- | :--- |
| 1 | 모델 (후보 8 → 사전 점검 6 → 비교 2) | 방법(M0) | qwen2.5:7b 유지 ([보고서](eval_v14_model_selection.md)) |
| 2 | 방법 (M0·M1·M2) — **실험 A** | 모델(qwen2.5:7b) | **M2 채택** |
| 3 | 모델 (qwen2.5:7b vs gemma4:12b) — **실험 B** | 방법(M2) | qwen2.5:7b 유지 |
| 4 | — | 최종 조합 | 최종 평가용 25건 1회 측정 |

### 3.2 연습 문제와 시험지를 다시 나눴다

v1.3 평가용 31건은 v1.3에서 결과를 이미 봤으므로 더 이상 "처음 보는 시험지"가 아니다. 63건을 모두 개발용(연습 문제)으로 돌리고, 새 시나리오 25건을 최종 평가용(시험지)으로 봉인했다([`final_v14_review.md`](../docs/dataset/final_v14_review.md)). 25건의 시나리오와 정답 라벨은 게임 개발 QA 실무 경험을 바탕으로 검토자가 시나리오를 제시하고, 2회 검토로 확정했다. 예를 들어 탈퇴 유예 중 계정 잠김, 길드장 위임 후 권한이 남는 문제, 환불 후 재화 미회수처럼 라이브 서비스에서 실제로 문제 되는 유형이다.

최종 평가용은 `--final` 옵션 없이 실행되지 않고, 비교 도구는 최종 평가용 문항이 섞인 실행을 판정하지 않는다. 시험지를 미리 보면 시험의 의미가 없어진다는 Test 세트 봉인 원칙([ML 08/14][ml0814], [ML 08/18][ml0818])과 데이터 누수 방지([PE 10/02][pe1002] 실습 6)를 코드로 강제한 것이다. 예시(M1)도 평가셋 88건과 표현이 겹치지 않는지 테스트로 확인했다(예시 오염 방지, [PE 10/02][pe1002]).

### 3.3 합격 기준을 측정 전에 커밋했다

방법, 예시 4개([`m1_examples.md`](../docs/method/m1_examples.md)), 체크리스트 질문, 채택 기준은 측정 전에 커밋했다(`171ba57`, `a94d1a7`). 결과를 보기 전에 선택 규칙을 고정한다는 원칙([ML 08/18][ml0818])이며, QA 실무로 보면 릴리스 판정 기준(Exit Criteria)을 테스트 시작 전에 합의해 두는 것과 같다.

| 구분 | 기준 | 쉽게 말하면 |
| :--- | :--- | :--- |
| 절대 기준 | 호출 성공 100%, 날조·허용 값 위반·출력 언어 위반 0, 평균 10초 이하 | 하나라도 걸리면 바로 탈락 |
| 기준선 대비 | X-2·X-3 누락이 같은 seed의 M0보다 늘지 않음 | 지금보다 나빠지면 탈락 |
| 회귀 기준 | X-1 증가 0, 처리·분류 정답 하락 0, 과잉 상신 증가 4 이하, 문항 단위 회귀 4 이하 등 | 잘 하던 걸 망가뜨리면 탈락 |
| 결정 | seed 3개 모두 통과 + Critical 누락 감소(같으면 우선순위 정답 증가) | 나빠지지 않은 것만으로는 바꾸지 않음 |

X-2·X-3을 "0건"이 아니라 "기준선보다 늘지 않음"으로 둔 이유는, 기준선 M0도 개발용 63건에서 X-3를 틀리기 때문이다. 0건을 요구하면 M0가 원래 틀리던 문항 때문에 모든 후보가 탈락해 더 나은 방법을 고를 수 없다. "어느 쪽이 더 나은가"(상대 비교)와 "실무에 써도 되는가"(0건 기준)를 나눠, 후자는 최종 측정에서 따로 판정했다(6절).

### 4.2 M1(모범 답안) — Critical은 가장 잘 잡았지만, 답안을 그대로 베꼈다

M1은 Critical 누락을 25건에서 9건으로 가장 많이 줄였다. 그런데도 탈락했다. 신입이 선배의 모범 티켓을 상황과 상관없이 그대로 복사해 쓰는 것과 같은 일이 생겼기 때문이다.

- **Critical 예시를 너무 넓게 적용했다.** 예시 E4는 "계정당 1회인 보상을 캐릭터를 바꿔 가며 반복 수령하는 악용"이었다. 이를 본 뒤 악용 정황만 있어도 Critical로 올렸다. 부계정 랭킹 몰아주기(S02), 핵 사용 신고(S18), 매크로 신고(B16), 보상 미지급(S14) 등이다. 다른 유저 제재 요청은 원래 CS로 넘길 일인데 리드 QA 사인 큐로 갔다. 과잉 상신이 26건에서 56건으로 늘었다.
- **예시의 모듈을 복사했다.** 예시 E4의 모듈 "결제·재화 / 보안·어뷰징"을 상관없는 문항에 21번 그대로 썼다. 모듈 정답률이 71.2%에서 55.8%로 떨어졌다.
- **형식이 흔들렸다.** seed마다 1건씩 응답 도중 다른 언어 문자가 섞였다.

계획서에 적어 둔 위험("예시 내용 복사", "프롬프트 길이 변화의 파급")이 그대로 나타났다. 7B 모델에게 예시는 "기준을 보여 주는 것"보다 "따라 할 답을 주는 것"으로 작동했다.

### 4.3 M2(체크리스트) — 올린 8건이 모두 진짜 Critical

| 항목 | 값 | 쉽게 말하면 |
| :--- | :--- | :--- |
| 체크리스트를 물은 응답 | 258 / 378 | 모델이 "결함"으로 분류한 건에만 물었다 |
| Critical로 올린 응답 | 8 (S04b 5, S16 2, S04 1) | 입장 횟수 초기화 악용, 길드전 동시 접속 끊김, 패배 기록 누락 |
| 그중 진짜 Critical | **8 / 8** | 잘못 올린 건은 0건 |
| "예"가 섞인 답 | 122 | 이 중 114는 이미 Critical로 판정된 건이라 설계대로 기록만 했다 |
| 1차 판정이 M0와 다른 응답 | 0 / 378 | M2의 변화는 순수하게 체크리스트 효과다 |

체크리스트의 답은 "예"로 기우는 경향이 있었다. 그래도 과잉 상신이 늘지 않은 이유는 두 가지 설계 덕분이다. 올리기만 하고 내리지 않는다는 규칙, 그리고 이미 Critical인 건은 답을 기록만 한다는 규칙이다. 만약 "체크리스트가 전부 아니오면 내린다"는 규칙을 넣었다면, 이 114건의 답이 판정을 흔들었을 것이다.

M2가 여전히 놓친 17건은 두 갈래다.

| 원인 | 응답 수 | 예 |
| :--- | :---: | :--- |
| 처음부터 "결함이 아니다"라고 분류해 체크리스트를 묻지 않음 | 10 | 지도의 분쟁 해역 명칭 오류(B20)를 "개선 제안"으로, 점검 후 장비 소실(S11)을 "버그 아님"으로 봄 |
| 체크리스트에 모두 "아니오"로 답함 | 7 | 패배 기록 누락(S04) 등 |

체크리스트는 분류가 맞을 때만 작동한다. 실무에서도 "버그 아님"으로 닫힌 이슈는 심각도 기준표를 거칠 기회가 없다. 분류 오류에서 시작된 누락은 이 방법으로 막을 수 없으며, v1.3에서 확인한 사람 확인 누락(X-3)과 같은 구조다.

| :--- | :---: | :---: | :--- |
| **Critical 누락 (X-1)** / 측정 120 | 17 | **0** | gemma는 Critical을 하나도 놓치지 않았다 |

gemma4:12b는 거의 모든 지표에서 앞섰다. 탈락 사유는 **잘 처리하던 이슈를 다르게 처리하기 시작한 것**이다.

| 기준 | seed 1 | seed 11 | seed 21 | 허용 |
| :--- | :---: | :---: | :---: | :---: |
| 처리 문항 단위 회귀 | 18 | 16 | 17 | ≤ 4 |
| 분류 문항 단위 회귀 | 7 | 6 | 6 | ≤ 4 |
| 과잉 상신 증가 | +4 | +7 | +6 | ≤ +4 |
| 사람 확인 누락 증가 | +1 | — | — | ≤ 0 |

바뀐 처리는 같은 문항에서 seed마다 반복됐다. 여러 결함이 섞인 제보(A11), 보상 미지급(S14), 지형 공략(S03), 단문 크래시(A02)를 긴급 사인 요청으로 올렸다. 또 결함인 글(난이도 의혹 A09·S20, 지형 공략 A20)을 "개선 제안"으로 분류해, A09는 사람 확인 없이 개발 배정으로 끝냈다. 모델 재선정 때와 같은 문항, 같은 성향이다([KL-004](../docs/issue_log.md#kl-004)).

**기준은 그대로 적용했다.** QA 실무에서도 새 빌드의 전체 통과율이 올라갔다고 회귀 결함을 넘기지 않는다. 이전 빌드에서 통과하던 케이스가 실패하면 그것은 회귀다. 문항 단위 회귀 기준은 이를 막으려고 둔 것이다. 또한 결과를 본 뒤 기준을 바꾸면 사전 등록의 의미가 사라진다. 원하는 결과가 아니어도 그대로 기록한다는 원칙([PE 10/02][pe1002]의 "차이가 없으면 없다고 기록한다")을 따랐다.

대신 이 결과를 v1.5의 근거로 남긴다. gemma4:12b는 "놓치지 않는 대신 자주 올리는" 담당자다. 실무에서 이런 담당자는 리드 QA의 확인 단계와 짝을 이루면 오히려 믿을 수 있다. 과잉 상신과 판단이 갈리는 건을 사람 검토 큐가 받아내는 구조라면, gemma4:12b는 "위험 건 누락 0건"에 가장 가까운 후보다.

### 6.2 해석

- **코드로 강제한 형식·절차는 이번에도 처음 보는 리포트에서 지켜졌다.** 날조, 결함 폐기, 형식 위반 0건이다. "모델은 판단하고, 형식과 절차는 코드가 강제한다"는 v1.3의 설계가 두 번째 시험지에서도 통했다.
- **놓친 Critical은 F01(탈퇴 철회 후 로그인 불가) 한 문항이다.** 두 회차 모두 Major로 판정했다. 체크리스트 1번 질문("게임 실행·로그인·메인 진행을 할 수 없고 우회 방법이 없는가")에도 "아니오"로 답했다. 실무에서 이 건은 3년 키운 계정에 접속할 수 없는 상황이라 CS 문의가 몰리고 계정 피해로 이어진다. 질문이 정확히 해당하는 상황에서도 모델이 적용하지 못한 사례다.
- **M2의 효과는 최종 세트에서 확인되지 않았다.** 체크리스트는 37응답에 물었지만 판정을 바꾼 건은 0건이다. 잡아낸 Critical 8/10은 모델이 1차 판정에서 이미 맞혔다. 따라서 이번 최종 결과를 "M2 덕분"이라고 말할 수 없다. 계획서에 적은 "개발용 개선 폭은 실제보다 크게 나올 수 있다"가 그대로 확인됐다. 개발 데이터로 고른 결과는 실제 성능을 과대평가한다는 원칙([ML 08/18][ml0818], [PE 10/02][pe1002] 실습 6)이 실제로 나타난 것이다.
- **과잉 상신 3건**은 강화 천장 의혹(F16) 2건과 재료 부족 교환 버튼(F17) 1건이다. F16은 판정 기준서 H-10("유저가 직접 검증할 수 없는 수치 의혹은 근거 없이 Critical로 올리지 않는다")을 따르지 않았다. QA 실무에서는 개발 QA가 테이블과 로그를 먼저 확인할 건이다.
- **참고: v1.3 최종 측정과의 비교** — Critical 누락 6/18 → 2/10, 사람 확인 누락 4/10 → 0/2로 줄었다. 다만 문항 세트가 다르고 측정 문항 수가 작아 개선의 근거로 쓰지 않는다.

### 6.3 개발용 안에서도 보이는 "연습 문제만 잘 푸는" 효과

개발용 63건을 v1.3 때의 분할로 다시 나눠 보면, 같은 방법(M2)인데도 결과가 크게 다르다.

| 지표 (M2, seed 3개 합계) | 옛 개발용 32건 (프롬프트를 맞춘 문항) | 옛 평가용 31건 |
| :--- | :---: | :---: |
| Critical 누락 | 1 / 66 | **16 / 54** |
| 사람 확인 누락 | 0 / 36 | **14 / 30** |
| 우선순위 정답률 | 76.0% | 48.4% |

프롬프트 v2.3은 옛 개발용 32건의 결과를 보며 다듬었다. 그 문항에서는 거의 틀리지 않고, 나머지 문항에서 오답이 몰렸다. 오답 노트로 외운 연습 문제는 맞히지만, 표현이 바뀐 문제는 못 푸는 것이다. 테스트 실무의 살충제 역설(같은 테스트만 반복하면 새로운 유형의 결함을 찾지 못한다)과 같은 현상이며, v1.3의 [KL-003](../docs/issue_log.md#kl-003)이 아직 해소되지 않았다는 뜻이다. 방법 비교에서 나온 개선 폭도 주로 옛 평가용 문항에서 생겼다.

테스트 실무에서는 테스트 도구의 오판이나 오류도 별도 결함으로 등록하고, 끝난 측정 결과를 고쳐 쓰지 않는다. ISSUE-010을 고칠 때도 "최종 측정 후에는 채점기를 고치지 않는다"는 규칙과 충돌하지 않도록 범위를 확인했다. 고친 것은 보고서 표를 그리는 부분뿐이다.

두 문제 모두 도구가 조용히 틀린 값을 내는 대신 **멈춰서** 드러났다. 이상이 있으면 숨기지 않고 실패로 드러낸다는 fail loud 원칙([PE 10/02][pe1002], [LC 10/01][lc1001])과, 같은 seed라도 실행 환경이 다르면 결과가 달라진다는 환경 재현성 원칙([LC 09/29][lc0929])에 따라 측정 환경 점검(`--strict-env`)과 비교 도구의 seed 구성 검사를 둔 덕분이다. OBS-004는 게임 QA에서 "직전 화면 상태"가 재현 조건에 포함되는 버그와 같다. 같은 seed의 재현은 같은 문항 순서까지 같을 때 성립한다.

## 8. 한계

- **최종 세트의 위험 건 측정 문항이 적다.** Critical 10응답(5문항), 사람 확인 2응답(1문항)이다. Critical 누락 2/10은 문항 하나의 결과이고, 사람 확인 누락 0/2만으로 경계 건 처리가 해결됐다고 말할 수 없다. 이 두 지표는 개발용 결과(각 120·66응답)를 함께 봐야 한다.
- **M2의 효과는 개발용에서만 확인됐다.** 최종 세트에서 체크리스트가 바꾼 판정은 없었다.
- **프롬프트 v2.3이 qwen2.5:7b의 옛 개발용 문항에 맞춰져 있다.** 실험 A의 M1·M2와 실험 B의 gemma4:12b 모두 이 프롬프트 위에서 측정했다([KL-004](../docs/issue_log.md#kl-004)).
- **seed 3개, 개발용 63건으로 판정했다.** seed 3개 모두에서 통과해야 채택하므로 한 번의 우연으로 채택되지는 않는다. 다만 문항 수가 작아 작은 차이는 문항 몇 개의 결과에 좌우된다.

## 10. 결론과 v1.5 과제

1. **체크리스트(M2)는 정확하지만 놓친 것을 찾는 힘이 약하다.** 올린 판정은 모두 맞았지만, 최종 세트에서는 판정을 바꾼 건이 없었다. 그리고 분류가 틀리면 아예 작동하지 않는다.
2. **예시(M1)는 효과가 크지만, 7B 모델은 예시를 베낀다.** Critical 인식은 가장 좋아졌지만 과잉 상신과 모듈 복사로 운영 품질이 나빠졌다.
3. **더 큰 모델(gemma4:12b)은 Critical을 놓치지 않지만, 현재 처리 절차와 어긋난다.** 넉넉하게 올리는 성향은 사람 확인 단계가 있으면 장점이 된다.
4. **v1.5 과제** — 모델 하나에 "놓치지 않으면서 과하게 올리지도 않는" 판단을 기대하기보다, 놓치지 않는 쪽으로 기운 판단을 사람 검토 큐가 받아내는 구조가 현실적이다. QA 조직에서 신입의 판정을 리드가 확인하는 구조와 같다. v1.5에서는 먼저 라벨 일치율과 LLM-as-judge의 신뢰도를 재고, 이어서 확신도·체크리스트 답·분류를 근거로 자동 등록과 사람 검토를 나누는 라우팅을 만든다. 실험 B의 gemma4:12b 결과와, 이미 Critical인 건에 대한 체크리스트 답 기록이 그 설계의 출발 자료다.
