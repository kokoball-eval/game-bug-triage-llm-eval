# 게임 버그 리포트 1차 트리아지 LLM 성능 및 품질 비교 분석서

본 문서는 가상 게임 **"Aether Raid"**의 버그 리포트 1차 트리아지 어시스턴트 선정을 위해 수행한 오픈소스 로컬 LLM 2종(`qwen2.5:7b`, `llama3.1:8b`)과 상용 클라우드 참조 모델(`gpt-5.6-luna`)의 벤치마크 평가 결과입니다.

> **결론 요약**
> * **선정**: Qwen2.5-7B (품질 81점 / 포맷 엄격 준수 100% / 평균 1.390초)
> * **탈락**: Llama-3.1-8B (77점) — 속도·단서 보존은 우수했으나 단문 리포트에서 환각 발생
> * **기준선**: gpt-5.6-luna (99점) — 로컬 모델의 한계를 재는 잣대로만 사용
>
> 선정 사유와 배포 계획만 필요하시면 [`report/final_selection.md`](final_selection.md)를 보세요.
> 이 문서는 **그 결론이 나온 측정 방법과 회차별 근거**를 담은 실무 레퍼런스입니다.

### 2) 평가 대상 모델 선정 기준 및 상세 제원

**1. 후보 선정 기준**

먼저 Use Case가 요구하는 4가지 필수 조건을 정리하고, 이를 기준으로 후보군을 좁혔습니다.

| 조건 | 판단 근거 | 실무 제약 |
| :--- | :--- | :--- |
| **로컬 구동 가능** | Ollama 공식 라이브러리에 태그가 존재해 폐쇄망 내 내려받기·실행이 가능한가 | 버그 리포트에 유저 계정(UID)과 미출시 콘텐츠가 포함되어 외부 API 전송 불가 |
| **8GB VRAM 단일 GPU 적재** | Q4 양자화 기준 모델 파일이 5 GB 내외인가 (시스템 RAM 오프로드 없이 전량 GPU 적재) | 별도 추론 서버 없이 QA 담당자 노트북에서 운용 |
| **한국어 처리** | 한국어 입출력이 가능한 Instruct 튜닝 버전인가 | 인입 리포트 원문이 한국어이고, 5개 필드 출력 지시를 따라야 함 |
| **상업적 이용 가능성** | 라이선스가 사내 상용 배포·수정·재배포를 허용하는가 | 게임 서비스 적용이 전제 |

이 조건을 만족하는 여러 후보 가운데 **성격이 대비되는 2종**을 최종 선정했습니다.

* **Llama-3.1-8B-Instruct (대조군)** — 오픈 LLM에서 가장 널리 채택된 기준선입니다. "일반적으로 무난한 선택"이 본 Use Case에서도 통하는지를 확인하기 위한 축입니다.
* **Qwen2.5-7B-Instruct (도전군)** — 한국어를 포함한 다국어 지원과 Apache 2.0 라이선스를 강점으로 내세운 대안입니다. 기준선을 넘어설 수 있는지 검증하기 위한 축입니다.

두 모델은 파라미터 규모(8.03B vs 7.61B)와 양자화 레벨(`Q4_K_M`)이 비슷합니다. 따라서 **모델 자체의 차이 외 변수(크기·양자화·런타임)를 통제한 상태로 비교**할 수 있습니다. 이 통제 가능성도 조합 선정의 근거였습니다.

> **선정 과정과 검증**
>
> 후보군은 위 요구 조건을 정리한 뒤 **LLM 도구의 제안을 출발점**으로 추렸습니다. 다만 제안받은 사양을 그대로 쓰지 않고, 최종 2종의 파라미터 규모·양자화·컨텍스트 길이·라이선스를 **Model Card 원문으로 직접 대조**했습니다.
>
> 이 대조 과정에서 실제로 오류를 한 건 잡았습니다. 초기에는 *"Qwen2.5-7B의 최대 context는 128K"* 로 알고 있었으나, Model Card 원문 확인 결과 **네이티브 32,768 토큰이며 YaRN rope scaling을 적용해야 약 131,072 토큰**이었습니다. 기본 설정에서는 확장이 적용되지 않으므로 위 제원표를 실제 값으로 정정했습니다.
>
> **한계**: Gemma·Mistral 계열 등 조건을 만족할 수 있는 다른 모델까지 폭넓게 탐색하지는 않았습니다. 5일 일정 안에서 후보 수를 늘리기보다 2종을 깊이 비교하는 쪽을 택했고, 후보 범위 확대는 후속 과제로 남깁니다.

> **자원 점유 및 Context 실측 안내**
>
> 40회 본 실험 로그(`local_eval_results.json`)에는 `ollama ps`의 `size_vram`만 기록되어 있습니다. 발제문이 요구하는 **시스템 RAM / VRAM 구분 기록**과 **실제 적용된 context length**는 `src/capture_env.py`로 사후 실측해 보완했습니다. 동일 모델 태그·동일 양자화 조건에서 수행한 읽기 전용 측정이므로 본 실험 집계 결과는 바뀌지 않았습니다. 측정 전문은 [`report/environment.md`](environment.md), 원본은 `data/results/environment.json`에 있습니다.
>
> 실측으로 확인한 사항은 세 가지입니다.
>
> 1. **두 모델 모두 시스템 RAM 점유 0 MiB, GPU 오프로드 100%** — RTX 5060 Laptop GPU(VRAM 8,151 MiB)에 전량 적재되어 CPU 분산 추론이 발생하지 않았습니다. 따라서 본 실험의 지연 시간·생성 속도는 CPU 오프로드 오버헤드가 섞이지 않은 순수 GPU 추론 조건에서 측정된 값입니다.
> 2. **실제 적용된 context length는 4,096 토큰** — 코드에서 `num_ctx`를 지정하지 않아 Ollama 기본값이 적용됐습니다. 초기에 기재했던 2,048 토큰은 실측으로 확인되지 않은 추정치였기에 정정했습니다.
> 3. **컨텍스트 잘림(truncation) 없음** — 동일 프롬프트에 대한 Cloud 실측 입력이 222~292 토큰, 로컬 최대 생성량이 193 토큰입니다. 합산 사용량이 4,096 한도 대비 충분히 여유 있습니다.

### 3) 평가 데이터셋 상세 (10문항)

문항은 정상 6건 · 경계 2건 · 정보 부족 2건으로 구성했습니다. 모델 간 차이를 실제로 드러낸 것은 경계·정보 부족 4건이었습니다.

**1. 정상 케이스 (Normal Cases — 6건)**

> 기본 기능 결함에 대해 심각도 판정, 모듈 분류, 도메인 단서 보존 능력을 검증합니다.

* **Q01: 챕터5 보스 패턴 3단계 크래시** `(Cloud 공통)`
  * **입력 원문**: `"전투 중 보스 패턴 3단계 진입 시 100% 크래시 발생. 재현: 챕터5 보스룸 입장 → 보스 체력 30% 이하 → 3단계 패턴 시작 즉시 앱 강제 종료. iOS 17.4, v2.3.1에서 확인."`
  * **검증 목적**: 최고 심각도(Blocker/Critical) 판정 및 환경 단서(iOS 17.4, v2.3.1) 보존 여부
* **Q02: 결제 후 다이아 미지급** `(Cloud 공통)`
  * **입력 원문**: `"결제 후 다이아가 지급되지 않음. 영수증은 있는데 재화가 반영 안 됨. 3명 유저가 동일 신고."`
  * **검증 목적**: 매출 직결 이슈 인식, 다중 피해(3명 유저) 단서 인지, 계정(UID)/주문번호 역질문
* **Q03: 설정 메뉴 사운드 오타**
  * **입력 원문**: `"설정 메뉴에서 '사운드' 텍스트가 '사운드ㄷ'로 오타 표시됨. 기능엔 영향 없음."`
  * **검증 목적**: 기능 무영향 텍스트 오류 인지 및 최하위 심각도(Trivial/Minor) 적정 통제
* **Q04: 특정 기종 로딩화면 텍스처 깨짐**
  * **입력 원문**: `"특정 갤럭시 기종(S21)에서만 로딩화면 텍스처가 깨져 보임. 다른 기종은 정상."`
  * **검증 목적**: 특정 기기 한정 결함(갤럭시 S21) 명시 및 적정 심각도(Minor) 부여
* **Q05: 간헐적 프레임 드랍**
  * **입력 원문**: `"가끔 전투 중 프레임이 뚝뚝 끊기는데 항상 그런 건 아니고 특정 스킬 쓸 때만 그런 것 같기도 함. 재현이 잘 안 됨."`
  * **검증 목적**: 재현 여부를 '간헐적'/'불명확'으로 처리하고 의심 스킬명 역질문 유도
* **Q10: 챕터5 보스룸 크래시 (Q01 중복 의심)** `(Cloud 공통)`
  * **입력 원문**: `"챕터5 보스 3단계에서 게임이 꺼짐. 이전에도 비슷한 신고가 있었던 것 같음(챕터5 보스룸 크래시)."`
  * **검증 목적**: 기존 유사 신고(Q01)와의 연관성 및 '중복 의심(Duplicate)' 감지 여부

**2. 경계 케이스 (Boundary Cases — 2건)**

> 복합 결함과 모호한 주관적 제보에 대한 분리·신중 판정 능력을 검증합니다.

* **Q06: 한 리포트에 3개 이슈 혼재** `(Cloud 공통)`
  * **입력 원문**: `"로그인 화면에서 튕기는 버그가 있고, 그리고 상점 아이콘도 안 눌리고, 친구 초대 보상도 안 옴."`
  * **검증 목적**: 3가지 개별 이슈(로그인 튕김, 상점 UI 먹통, 초대 보상 누락) 분리 식별 및 티켓 분할 권고
* **Q07: 업데이트 후 모호한 성능 불만**

### 4) 벤치마크 코드 구성과 설계 의도

측정 결과만큼 **어떻게 측정했는지**가 중요하므로, 실험 코드의 구조와 각 설계 판단의 이유를 기록합니다.

#### 실행 흐름

```text
[1일차] 01_ollama_chat.py    단일 호출 스모크 테스트 → *_verify.json
            │                (모델 적재 가능 여부·기본 출력 성향 확인)
            ▼
[2일차] run_eval.py          워밍업 1회 분리 → 10문항 × 2모델 × 2회 = 40회
            │                → local_eval_results.json
            ▼
[3일차] 02_luna_chat.py      Cloud 공통 5문항 × 1회 → cloud_eval_results.json
            │
            ▼
[4일차] test_fewshot.py      Q08 Few-Shot 교정 검증 → fewshot_verify.json
            │
            ▼
[사후]  score_format.py      원본 로그 재채점 → format_compliance.json / .md
        summarize_eval.py    원본 로그 재집계 → benchmark_summary.json
        capture_env.py       런타임 실측       → environment.json / .md
```

앞의 네 개는 **모델을 호출해 로그를 만드는** 스크립트이고, 뒤의 세 개는 **그 로그를 읽어 산출물을 만드는** 스크립트입니다. 이 분리가 핵심입니다. 문서에 적는 수치는 전부 뒤쪽 세 개가 만들어내므로, 실험을 다시 돌리지 않고도 언제든 대조할 수 있습니다.

#### 설계 판단과 이유

| 판단 | 왜 그렇게 했나 | 그러지 않았다면 |
| :--- | :--- | :--- |
| **`chat()` 대신 `generate()` + 문자열 결합** | `chat()`은 모델별 chat 템플릿으로 메시지를 조립하므로, 같은 메시지를 넣어도 지시문의 위치와 구분자가 모델마다 달라집니다. 직접 조립해 **통제 대상인 부분(시스템 지시문 + 리포트 본문)을 두 모델에 같은 순서·같은 글자로** 고정했습니다. 다만 `generate()`도 `raw=True`가 아니면 모델 고유 템플릿은 적용됩니다 — 그 포장은 각 모델의 정상 동작이라 그대로 뒀습니다 | 입력이 다른 상태로 출력을 비교하게 되어 비교 자체가 무효 |
| **워밍업 1회를 `warmup_runs` 키로 분리 저장** | 첫 호출에는 디스크→VRAM 적재 시간(2~3초)이 붙습니다. 본 통계에서 제외하되 로딩 시간 자체는 별도 지표로 보고 | 먼저 호출한 모델이 무조건 느려 보임 |
| **`eval_duration <= 0`이면 `tokens_per_sec = None`** | 계산 불가를 0으로 대체하면 "속도가 0이었다"는 뜻이 되어 평균이 무너집니다. 결측은 결측으로 기록 | 평균 속도가 실제보다 낮게 집계 |
| **예외를 잡아 `success: False`로 기록하고 진행** | 한 건이 실패해도 40회 배치가 중단되지 않고, 실패 사유가 로그에 남습니다 | 중간 실패 시 전체 재실행, 실패 원인 유실 |
| **매 호출 직후 `ollama ps`로 VRAM 측정** | 모델이 실제로 적재된 상태의 점유량을 기록 | 추론과 무관한 시점의 값이 섞임 |
| **생성 파라미터를 파일 상단 상수(`OPTIONS`)로 고정** | 두 모델에 동일한 값이 적용됨을 코드로 보장 | 모델별로 다른 값이 들어가도 알아채기 어려움 |
| **결과를 `metadata` + `warmup_runs` + `results` 구조로 저장** | 사후에 조건을 바꿔 재집계할 수 있는 형태 | 집계된 숫자만 남아 재검증 불가 |
| **API 키는 환경변수 우선, 없으면 `getpass`** | 키가 코드·저장소·터미널 기록·화면 공유 어디에도 남지 않습니다 | 실험 로그나 스크린샷에 키 노출 |

#### 채점 스크립트를 따로 둔 이유

**`score_format.py` — 규칙을 R1~R6으로 쪼갠 것**이 핵심입니다. "포맷을 지켰다/안 지켰다"를 한 덩어리로 판정하면 준수율은 나오지만 **왜 실패했는지**는 알 수 없습니다. 규칙별로 쪼개 채점했기 때문에 Llama의 실패가 전부 `R4(필드 사이 빈 줄)` 하나이고 `R1(서두 사족)`은 45건 전수 0건이라는 사실을 밝힐 수 있었습니다. 엄격 기준과 파서 호환 기준이라는 이중 지표도 여기서 나왔습니다.

**`test_fewshot.py` — 교정 성공 여부를 눈으로 판단하지 않기 위해** 4개 항목(심각도 판단보류 / 재현 여부 불명확 / 역질문 키워드 2개 이상 / 서두 사족 없음)을 기계적으로 검사하고 판정 근거를 JSON에 남깁니다.

**`capture_env.py` — 본 실험 로그를 건드리지 않고 보완하기 위해** 사후 측정 방식을 택했습니다. 40회 로그에는 `size_vram`만 있어 시스템 RAM 구분과 실제 context length를 알 수 없었는데, 재실험 대신 동일 조건에서 읽기 전용으로 측정해 채웠습니다.

**`summarize_eval.py` — 집계 정의를 코드로 고정하기 위해** 만들었습니다. "평균 속도"가 단순평균인지 가중평균인지, 워밍업을 포함하는지, 10문항인지 Cloud 공통 5문항인지가 정해져 있지 않으면 계산할 때마다 다른 값이 나옵니다. 정의를 docstring과 코드에 못 박고, 문서 수치는 이 스크립트 출력과 일치해야 합니다.

### 2) QA 평가 및 분석 관점

**포맷 계약 준수율 (Formatting Contract)** — Qwen은 사족 없이 규격으로 직행했습니다. Llama는 챗봇형 안내 문구를 노출했습니다. 다만 Llama의 사족은 프롬프트 네거티브 지시로 제어 가능한 영역으로 판단했습니다.

**고유명사 무결성 (Terminology Integrity)** — Llama는 인게임 지명 `스피릿 아일랜드`를 보존한 반면, Qwen은 `스플릿 아일랜드`로 오독했습니다. 담당 부서 오배정을 막아야 하는 버그 트래킹 특성상 Llama가 적합합니다.

**카테고리 매핑 및 스키마 준수 (Schema Contract)** — Llama는 시스템이 지정한 복합 라벨(`Crash/Freeze`)을 그대로 유지해 Jira Enum 검증을 통과할 수 있습니다. Qwen은 임의 축약(`Crash`)으로 API 예외 위험이 확인됐습니다.

**토큰 생성 처리량 (Token Generation Throughput)** — Llama가 66.51 tokens/s로 Qwen(64.56 tokens/s)보다 디코딩 처리량이 앞섰습니다.

**최종 응답 지연 시간 (Wall-clock Latency)** — Qwen은 3.807초(100토큰)로 Llama(5.060초, 115토큰)보다 약 25% 빨랐습니다.

* 다만 1일차는 단일 호출이라 두 값 모두 콜드 스타트 로딩 시간(Qwen 2.124초, Llama 3.198초)을 포함합니다. **순수 응답 지연으로 해석하면 안 됩니다.**
* 로딩을 제외한 생성 구간만 보면 Llama가 근소하게 빠릅니다(66.51 vs 64.56 tokens/s).
* 그래서 **본 실험에서는 워밍업을 분리해 다시 측정하기로** 했습니다.

**하드웨어 운영 마진 (VRAM Safety Margin)** — Qwen 4.42 GB vs Llama 4.91 GB로 Qwen이 약 499 MiB 적게 점유합니다. 본 장비에서는 두 모델 모두 적재 가능하므로 당락 조건은 아니며, 컨텍스트 확장·동시 구동·저사양 이식 시의 여유분으로 해석해야 합니다.

### 3) 1일차 결론 및 가설 수립

> 1. Llama-3.1은 고유명사 보존, 스키마 일치, 순수 연산 속도(TPS)에서 Qwen2.5-7B보다 우위를 보였습니다.
> 2. 유일한 단점인 '서두 사족'만 프롬프트 네거티브 가드레일로 제어하면, **Llama가 본 실험의 최종 승자가 될 것**으로 판단했습니다.

### 3) QA 평가 및 분석 관점 (7개 항목)

**1. 포맷 계약 준수율 및 가드레일 한계 (Formatting Contract & Guardrail Limits)**
`[ Qwen 2.5-7B 우세 ]`

* **현상** — 가드레일 주입 후 Qwen은 20회 전수에서 빈 줄·사족 없이 5개 필드 규격을 100% 준수했습니다. Llama도 1일차에 문제였던 **서두 사족은 0건으로 통제**됐습니다. 다만 20회 중 19회에서 필드 사이에 빈 줄을 삽입해, 엄격 기준 준수율은 5%(1/20), 빈 줄을 허용하는 파서 호환 기준으로는 100%(20/20)로 측정됐습니다. (`src/score_format.py` 자동 채점, 근거: [`report/format_compliance.md`](format_compliance.md))
* **실무 영향** — Llama도 필드 누락·순서 오류·Enum 위반은 0건이라 파싱 자체는 가능합니다. 다만 동일 프롬프트·동일 설정에서 Q05(간헐적 프레임 드랍)의 2회차 실행 한 번만 빈 줄 없이 출력되는 등 개행 스타일이 회차마다 흔들립니다. 줄 단위 파서에는 빈 줄 정규화 전처리가 필요합니다.
* **판정** — **Qwen 우세.** 파싱 에러 0건으로 백엔드 파이프라인 안전성 확보.

**2. 고유명사 및 도메인 맥락 보존 (Terminology & Context Awareness)**
`[ Llama-3.1-8B 우세 ]`

* **현상** — Llama는 Q01의 환경 단서(iOS 17.4, v2.3.1)와 Q10의 중복 의심 단서("이전 신고와의 연관성 확인 필요")를 전 회차에서 보존했습니다. Qwen은 세부 단서를 단순화하거나 중복 연관성을 누락했습니다.
* **실무 영향** — 도메인 고유명사 보존과 유사 티켓 연관성 감지는 Llama가 우수해 중복 티켓 누적 방지에 유리합니다.
* **판정** — **Llama 우세.** 복합 맥락 파악 및 도메인 단서 추출 역량 우수.

**3. 카테고리 매핑 및 스키마 준수 (Schema Contract)**
`[ Llama-3.1-8B 우세 ]`

* **현상** — 복합 결함 선택지에서 Llama는 시스템이 정의한 원문 라벨을 유지했습니다. Qwen은 개별 하위 속성으로 정제하려는 변형 성향을 보였습니다.
* **실무 영향** — Jira 드롭다운 Enum 규격과 일치시키는 관점에서는 원문 라벨을 보존하는 Llama의 보수적 태도가 API 연동에 적합합니다.
* **판정** — **Llama 우세.** 사전 정의된 스키마 무결성 유지.

**4. 토큰 생성 처리량 (Token Generation Throughput)**
`[ Llama-3.1-8B 우세 ]`

* **현상** — Llama의 초당 디코딩 속도는 66.56 tokens/s로 Qwen(57.68 tokens/s)보다 약 15% 앞섰습니다.
* **실무 영향** — 1일차 가설대로 순수 GPU 연산 처리량 자체는 파라미터 크기(8B)에도 불구하고 Llama가 앞섬을 대규모 표본에서 확인했습니다.
* **판정** — **Llama 우세.** 하드웨어 디코딩 연산 능력 우위.

**5. 최종 응답 지연 시간의 역설 (Latency Paradox)**
`[ Qwen 2.5-7B 우세 ]`

* **현상** — 순수 속도는 Llama가 15% 빨랐습니다. 그러나 상세 서술 성향으로 평균 117.6토큰을 소모해 1.809초가 걸렸습니다. Qwen은 핵심만 76.4토큰으로 압축해 1.390초에 응답을 마쳤습니다. 약 23% 더 빠릅니다.
* **실무 영향** — 1일차 가설("가드레일로 Llama의 토큰 수를 줄여 레이턴시를 역전시킨다")은 검증 결과 기각됐습니다. Llama의 다변 성향은 프롬프트로 억제되지 않았습니다.
* **판정** — **Qwen 우세.** 토큰 압축으로 최종 대기 시간 단축.

**6. 하드웨어 운영 마진 (VRAM Safety Margin)**
`[ Qwen 2.5-7B 소폭 우세 — 본 장비에서는 당락 조건 아님 ]`

* **현상** — 40회 연속 실행 동안 Qwen은 4,528.1 MiB, Llama는 5,027.5 MiB를 점유했습니다. **두 모델 모두 시스템 RAM 오프로드 없이 100% GPU에 적재**됐습니다. (실측: [`report/environment.md`](environment.md))
* **실무 영향** — 본 장비(RTX 5060 Laptop, VRAM 8,151 MiB) 기준 잔여 VRAM은 Qwen 3,623 MiB, Llama 3,124 MiB입니다. 여기서 OS·데스크톱이 상시 점유하는 약 522 MiB를 빼면 실사용 여유는 각각 약 3,101 MiB, 2,601 MiB입니다. 즉 **이번 환경에서 VRAM은 두 모델의 당락을 가른 제약이 아니었으며**, 최종 선정을 가른 것은 데이터 무결성(항목 7)입니다. 다만 Qwen이 상시 499 MiB를 덜 점유한다는 사실은 다음 세 조건에서 여유분으로 작용합니다.
  1. **컨텍스트 확장 시** — 현재 실측 context는 4,096 토큰입니다. 긴 오류 로그가 첨부된 리포트를 처리하려 context를 키우면 KV 캐시가 함께 증가하므로, 기본 점유가 작은 쪽이 더 긴 입력을 GPU에 유지할 수 있습니다.
  2. **동시 구동 시** — 게임 클라이언트·빌드 툴 등 GPU를 함께 쓰는 프로세스와 병행할 때 여유분이 완충 역할을 합니다.
  3. **저사양 이식 시** — VRAM 6 GB급 보급형 GPU로 옮길 때 499 MiB는 전량 GPU 적재 여부를 가를 수 있는 크기입니다.
* **판정** — **Qwen 소폭 우세.** 동일 장비에서는 결정적 차이가 아니며, 컨텍스트 확장·저사양 이식 시의 이점입니다.

**7. 치명적 결함 — 정보 부족 대응과 환각 리스크 (Fallback & Critical Hallucination)**
`[ Qwen 2.5-7B 우세 — 최종 선정을 가른 항목 ]`

* **현상** — 정보가 극도로 부족한 단문 리포트(Q08: `"크래시남"`) 인입 시, Llama는 원문에 없는 결함("전투 모드 무한 이동")과 PC 사양("GTX 1660 Ti")을 날조했습니다(Hallucination). Qwen은 소극적 대응(`누락 정보: 없음`)과 2회차 경미한 비문("앱이 발생하고 있습니다")에 그쳤습니다.
* **실무 영향** — Qwen의 소극성은 룰셋이나 Few-Shot 1건으로 교정 가능한 범주로 판단했습니다(4일차에 실측 검증). 반면 Llama가 확신을 갖고 허위 결함을 등록하는 것은 QA·개발 리소스를 낭비시키는 통제 불능의 결함입니다.
* **판정** — **Qwen 결정적 우세.** Llama 최종 탈락 및 Qwen 채택의 핵심 사유.

### 4) 2일차 결론

> 1. 가드레일을 적용해도 Llama의 다변 성향(117.6토큰 소모)은 통제되지 않았습니다. 최종 지연 시간은 핵심만 압축 출력한 Qwen(1.390초)이 Llama(1.809초)보다 23% 빨랐습니다.
> 2. 단문 리포트(Q08)에서 Llama가 없는 버그와 PC 스펙을 날조하는 환각이 발견됐습니다. 프롬프트만으로 통제할 수 없는 고위험 결함으로 판단했습니다.
> 3. Qwen의 소극적 대응은 룰셋과 Few-Shot으로 교정 가능한 범위로 추정했습니다. 데이터 무결성 기준에서 **Qwen2.5가 유일한 실무 대안**이라는 결론에 도달했습니다.

## 5. 클라우드 대조군 비교 및 심층 분석 (3일차)

로컬 7B~8B 소형 모델의 성능 상한선(Ceiling)과 실무 적합성을 확인하기 위해, 동일 프롬프트 조건에서 상용 클라우드 모델(`gpt-5.6-luna`)을 대조군으로 투입했습니다. 공통 5개 문항(`Q01, Q02, Q06, Q08, Q10`)에 대한 3자 비교입니다.

> **표본 수($n$) 기준 안내**
> 로컬 모델은 반복 안정성 검증을 위해 문항당 2회($n=2$, 5개 문항 총 10회), Cloud API는 기준선 확인을 위해 문항당 1회($n=1$, 총 5회)로 측정했습니다. 로컬의 특정 우수 회차만 선별하지 않고 전수를 대조했습니다.

### 1) 3일차 검증 가설 및 검증 결과

**사전 가설 (실험 전)**

1. 상용 클라우드 모델(`gpt-5.6-luna`)은 로컬 소형 모델이 취약했던 2대 한계, 즉 **복합 결함 분할(Q06)**과 **단문 리포트 Fallback 역질문(Q08)**을 해결해 이상적인 QA 트리아지 기준선(Gold Standard)을 보여줄 것이다.
2. 로컬 모델 단독으로는 클라우드 수준의 복합 추론을 대체할 수 없으므로, 클라우드의 판단 로직을 모사하기 위한 **전·후처리 아키텍처(이슈 스플리터, Few-Shot 가드레일)**가 프로덕션 배포에 필수적일 것이다.

**검증 결과 (실험 후)**

* **가설 입증** — Cloud 모델은 로그인 크래시를 Blocker로 격상해 3개 이슈를 분리 검증하도록 지시했고, 단문 리포트에서도 환각 없이 5대 필수 역질문을 제시했습니다.
* **보완 아키텍처 도출** — 단일 로컬 LLM의 파라미터 한계를 실측하고, 3대 프로덕션 가드레일(Few-Shot 주입, Two-Stage 이슈 분할기, Human-in-the-Loop) 도입의 기술적 당위성을 확보했습니다.

| **생성 토큰 수** | **82.3 tokens (핵심 압축)** | 129.8 tokens (상세 서술) | 233.4 tokens (심층 분석 가이드) | **용도별 분기**<br>Qwen: 정형 파싱 최적화 / Cloud: 상세 가이드 |
| **총 소요 시간 (Latency)** | **1.481초** | 1.989초 | 4.079초 (네트워크 RTT 포함) | **로컬 우세 (Qwen 1위)**<br>온프레미스가 Cloud 대비 약 2.8배 신속 |
| **VRAM 점유량** | **4,528.1 MiB (~4.42 GB)** | 5,027.5 MiB (~4.91 GB) | **0 MiB (서버리스 인프라)** | **로컬 마진은 Qwen 소폭 우세**<br>Llama 대비 499 MiB 절약 (양쪽 모두 100% GPU 적재) |

#### 💡 지표 해석 — Cloud API의 `0 MiB`와 `N/A`가 뜻하는 것

**1. `0 MiB (Serverless)` — 하드웨어 자원의 추상화**

* **의미** — 로컬 PC의 GPU 메모리를 전혀 사용하지 않습니다. 모델이 원격 서버에서 구동되기 때문입니다.
* **비즈니스 임팩트** — 사내 PC에 GPU가 없어도 대형 LLM을 쓸 수 있고, 게임 엔진 같은 무거운 프로그램과 동시 실행해도 OOM 크래시가 발생하지 않습니다. 인프라 관리 부담이 없습니다.
* **트레이드오프** — 클라우드는 하드웨어 셋업 비용이 없는 대신 트래픽에 비례한 토큰 호출 비용이 계속 발생합니다. 로컬 모델(Qwen)은 4.42 GB의 VRAM을 점유하지만, **미공개 빌드 정보나 유저 계정(UID)을 외부로 보내지 않아도 된다**는 이점이 있습니다.

**2. `N/A (Serverless)` — 순수 디코딩 속도를 잴 수 없음**

* **의미** — 초당 토큰 생성 속도(TPS)를 순수하게 측정할 수 없습니다.
* **기술적 이유** — 로컬 모델은 GPU 연산 속도를 정확히 잴 수 있지만, 클라우드 API 측정치에는 ① 인터넷 왕복 시간(RTT), ② 서버 트래픽 대기열, ③ 서버 분산 처리 로직이 모두 섞입니다. 이를 토큰 수로 나눠 TPS를 구하면 '네트워크 지연이 포함된 체감 속도'가 되어, 로컬 TPS와 1:1 비교하는 것 자체가 통계적 오류입니다.
* **결론** — 클라우드 서버의 연산 성능은 강력합니다. 그러나 네트워크 지연 때문에 **최종 지연 시간은 Cloud 4.079초 대 로컬(Qwen) 1.481초로 약 2.8배 차이**였습니다(동일 5문항 기준). 실시간으로 인입되는 인게임 버그 리포트를 즉각 트리아지하려면 처리 속도를 직접 통제할 수 있는 **로컬 모델이 유리**하다는 실측 근거입니다.

### 4) QA 엔지니어링 관점 심층 분석

**1. 정보 부족 대응(Fallback)의 대조 — Q08 단문 '크래시남'**
`[ Cloud 우세 / Qwen 방어적 차선 / Llama 치명적 결함 ]`

* **현상** — Cloud는 성급한 판정을 유보하고 `심각도: 판단보류`, `재현 여부: 불명확`을 선언한 뒤 필수 5대 역질문(시점, 절차, 덤프, OS, 버전)을 출력했습니다. Llama는 없는 결함과 기기 사양을 날조했습니다. Qwen은 비문 출력과 소극적 침묵에 그쳤습니다.
* **실무 영향** — Llama의 날조는 버그 데이터베이스를 오염시켜 QA·개발팀의 공수를 낭비시킵니다. 로컬 모델 중에서는 소극적이지만 날조하지 않는 Qwen에 Few-Shot 가드레일을 보완하는 것이 현실적인 대안입니다.
* **판정** — **Cloud 우세.** 로컬 도입 시 Qwen 기반 가드레일 설계의 당위성 확보.

**2. 복합 결함 분할 및 심각도 우선순위 — Q06 복합 3건**
`[ Cloud 우세 ]`

* **현상** — 3개 결함(로그인 튕김, 상점 미작동, 초대 보상 누락)이 혼재된 리포트에 대해 로컬 2종은 모두 단일 모듈('UI')로 축소 분류했습니다. Cloud 모델은 로그인 불가 현상을 포착해 심각도를 `Blocker`로 격상하고, 3개 이슈를 개별 분리해 검증하도록 지시했습니다.
* **실무 영향** — 단일 티켓으로 묶여 긴급 크래시가 묻히는 사고를 막으려면, 단일 프롬프트 처리보다 **1차 이슈 스플리터 전처리 파이프라인**이 필요합니다.
* **판정** — **Cloud 우세.** 프로덕션 2단계 파이프라인 설계 필요성 입증.

**3. 재현율 판정의 현실성과 검증 신중성 — Q02 결제 미지급**
`[ Cloud 우세 ]`

* **현상** — 유저 3명의 신고 문구에 대해 로컬 모델들은 텍스트 그대로 `발생(100%)`으로 단정했습니다. Cloud 모델은 사내 재현 검증과 로그 확인이 아직 안 된 VOC 단계임을 인지하고 `재현 여부: 불명확`으로 판정했습니다.
* **실무 영향** — 외부 리포트를 확정 버그로 단정하면 담당 엔지니어 배정 후 헛걸음 검증이 발생합니다. 트리아지 단계의 신중한 판정 룰셋이 필요합니다.
* **판정** — **Cloud 우세.** QA 도메인 맥락 기반의 엄격한 판정 기준 유지.

**4. 유사 결함 및 중복 티켓 감지 역량 — Q10 중복 의심**
`[ Cloud & Llama 공동 우세 / Qwen 미흡 ]`

* **현상** — Q01과 연관된 유사 제보에 대해 Cloud와 Llama는 모두 `"이전 신고와의 연관성 및 중복 여부 확인"`을 명시했습니다. Qwen은 단순 권장 조치만 나열하며 중복 단서를 누락했습니다.
* **실무 영향** — 중복 티켓 발행 방지 측면에서는 Llama와 Cloud의 맥락 추론이 앞섭니다. Qwen을 실무에 쓴다면 벡터 DB 기반 유사 티켓 검색(RAG) 전처리로 보완해야 합니다.
* **판정** — **Cloud & Llama 우세.** 맥락 인지 및 중복 필터링 역량 입증.
