# 게임 버그 리포트 1차 트리아지 LLM 성능 및 품질 비교 분석서

본 문서는 가상 게임 **"Aether Raid"**의 버그 리포트 1차 트리아지 어시스턴트 선정을 위해 수행된 오픈소스 로컬 LLM 2종(`qwen2.5:7b`, `llama3.1:8b`) 및 상용 클라우드 참조 모델(`gpt-5.6-luna`)의 벤치마크 평가 결과를 정리한 보고서입니다.

## 1. 평가 환경 및 데이터셋 개요

### 1) 실행 환경 및 데이터셋 구성
* **실행 환경**: Windows 11, 단일 외장 GPU (VRAM < 8GB), Ollama 추론 런타임, Python 3.12 (`uv`)
* **평가 데이터셋 (`data/questions.json`)**: 총 10건 고정 질문
  * **정상 케이스 (6건)**: 크래시(Q01), 결제 미지급(Q02), UI 오타(Q03), 기기 한정 결함(Q04), 프레임 드랍(Q05), 중복 의심(Q10)
  * **경계 케이스 (2건)**: 복합 이슈 혼재(Q06), 모호한 성능 불만(Q07)
  * **정보 부족/Fallback (2건)**: 단문 리포트(Q08), 세이브 유실(Q09)
* **표본 크기 ($n$)**:
  * **로컬 모델**: 모델당 20회 (10문항 × 2회 반복, 사전 워밍업 1회 분리 집계)
  * **클라우드 모델**: 사전 지정 5문항(`Q01`, `Q02`, `Q06`, `Q08`, `Q10`) × 1회

### 2) 1일차 검증 기반 가설 수립
> 1. Llama-3.1은 고유명사 보존, 스키마 일치, 순수 연산 속도(TPS)에서 Qwen2.5-7B 대비 명확한 우위를 보임.
> 2. 유일한 단점인 '서두 사족'만 프롬프트 네거티브 가드레일로 제어한다면, Llama가 본 실험의 최종 승자가 될 것으로 판단함.

### 3) QA 평가 및 분석 관점
* **포맷 계약 준수율 (Formatting Contract)**: Qwen은 사족 없이 규격으로 직행했으나, Llama는 챗봇형 안내 문구를 노출함. 단, Llama의 사족은 프롬프트 네거티브 지시로 제어 가능한 영역으로 판단.
* **고유명사 무결성 (Terminology Integrity)**: Llama는 인게임 지명 `'스피릿 아일랜드'`를 완벽히 보존한 반면, Qwen은 `'스플릿 아일랜드'`로 오독함. 담당 부서 오배정을 막아야 하는 버그 트래킹 특성상 Llama가 적합.
* **카테고리 매핑 및 스키마 준수 (Schema Contract)**: Llama는 시스템이 지정한 복합 라벨(`Crash/Freeze`)을 100% 보존하여 Jira Enum 검증 통과 가능. Qwen은 임의 축약(`Crash`)으로 API 예외 위험 확인.
* **토큰 생성 처리량 (Token Generation Throughput)**: Llama가 66.51 tokens/s로 Qwen(64.56 tokens/s) 대비 하드웨어 연산 디코딩 처리량 우세.
* **최종 응답 지연 시간 (Wall-clock Latency)**: Qwen은 0.74초(48토큰)로 Llama(1.22초, 81토큰)보다 39% 신속. Llama의 사족 생성을 억제하면 속도 역전이 가능할 것으로 가설 수립.
* **하드웨어 운영 마진 (VRAM Safety Margin)**: Qwen 4.42 GB vs Llama 4.91 GB로, 8GB 이하 보급형 PC 환경에서 Qwen이 약 500 MiB의 안전 마진을 확보.

> 1. 가드레일을 적용해도 Llama 본연의 다변 성향(117.6토큰 소모)은 통제되지 않아, 최종 지연 시간은 핵심만 압축 출력한 Qwen(1.39초)이 Llama(1.81초)보다 23% 빨랐습니다.

> 3. Qwen의 소극적 대응은 룰셋과 Few-Shot으로 100% 교정 가능한 범위로 추정, 데이터 무결성 기준에서 Qwen2.5가 유일한 실무 대안이라는 결론을 낼 수 있었습니다.

### 4) QA 평가 및 분석 관점

**1. 포맷 계약 준수율 및 가드레일 한계 (Formatting Contract & Guardrail Limits)**  
`[ Qwen 2.5-7B 우세 ]`
* **현상**: 네거티브 가드레일 주입 후 Qwen은 20회 전수 실행에서 사족 없이 5개 필드 규격을 100% 준수. 반면 Llama는 5회차에서 여전히 불필요한 개행이나 서두 문구를 노출(준수율 75%).
* **실무 영향**: Llama의 챗봇형 대화 습관은 단순 시스템 프롬프트 제약만으로 완전 통제가 어려우며, 정규식 파서 예외 위험이 상존함.
* **판정**: **Qwen 우세** (파싱 에러 제로 달성으로 백엔드 파이프라인 안전성 확보).

**2. 고유명사 및 도메인 맥락 보존 (Terminology & Context Awareness)**  
`[ Llama-3.1-8B 우세 ]`
* **현상**: Llama는 Q01의 환경 단서(iOS 17.4, v2.3.1)와 Q10의 유사·중복 의심 단서("이전 신고와의 연관성 확인 필요")를 전 회차에서 완벽 보존. 반면 Qwen은 세부 단서를 단순화하거나 중복 연관성을 누락.
* **실무 영향**: 도메인 고유명사 보존과 유사 티켓 연관성 감지 능력은 Llama가 우수하여 중복 티켓 누적 방지에 유리.
* **판정**: **Llama 우세** (복합 맥락 파악 및 도메인 단서 추출 역량 탁월).

**3. 카테고리 매핑 및 스키마 준수 (Schema Contract)**  
`[ Llama-3.1-8B 우세 ]`
* **현상**: 복합 결함 선택지에서 Llama는 시스템이 정의한 원문 라벨을 엄격히 유지. Qwen은 개별 하위 속성으로 정제하려는 자의적 변형 성향 유지.
* **실무 영향**: Jira 드롭다운 Enum 규격과 일치시키는 관점에서는 원문 라벨을 보존하는 Llama의 보수적 태도가 API 연동에 더 적합.
* **판정**: **Llama 우세** (사전 정의된 스키마 무결성 유지).

**4. 토큰 생성 처리량 (Token Generation Throughput)**  
`[ Llama-3.1-8B 우세 ]`
* **현상**: Llama의 초당 디코딩 속도는 66.52 tokens/s로 Qwen(58.74 tokens/s) 대비 약 13% 우세.
* **실무 영향**: 1일차 가설대로 순수 GPU 연산 처리량 자체는 파라미터 크기(8B)에도 불구하고 Llama가 앞섬을 대규모 표본에서 통계적으로 입증.
* **판정**: **Llama 우세** (하드웨어 디코딩 연산 능력 우위).

**5. 최종 응답 지연 시간의 역설 (Latency Paradox)**  
`[ Qwen 2.5-7B 우세 ]`
* **현상**: 순수 속도는 Llama가 13% 빨랐으나, 상세 서술 성향으로 인해 평균 117.6토큰을 소모하며 1.809초 소요. Qwen은 핵심만 76.5토큰으로 압축하여 1.390초 만에 응답 완료(약 23% 더 신속).
* **실무 영향**: 1일차 가설("가드레일로 Llama의 토큰 수를 줄여 레이턴시를 역전시킨다")을 검증한 결과, Llama의 본질적인 다변 성향은 억제되지 않음.
* **판정**: **Qwen 우세** (오버헤드 없는 토큰 압축으로 최종 대기 시간 단축).

**6. 하드웨어 운영 마진 (VRAM Safety Margin)**  
`[ Qwen 2.5-7B 우세 ]`
* **현상**: 40회 연속 실행 동안 Qwen은 4.42 GB, Llama는 4.91 GB 점유 유지.
* **실무 영향**: 8GB 미만 보급형 GPU 환경에서 Qwen이 확보한 약 500 MiB의 여유 마진은 다중 프로세스 동작 환경에서 무중단 서빙의 핵심 안전판 역할 수행.
* **판정**: **Qwen 우세** (로컬 온프레미스 인프라 안정성 우위).

**7. 치명적 결함: 정보 부족 대응과 환각 리스크 (Fallback & Critical Hallucination)**

#### 💡 [지표 심층 해석] Cloud API의 `0 MiB` 및 `N/A`가 시사하는 바

**1. `0 MiB (Serverless)`의 해석: 하드웨어 자원의 추상화와 오프로딩(Offloading)**
* **의미**: 로컬 PC의 그래픽카드(GPU) 메모리를 단 1MB도 사용하지 않음을 의미합니다. 모델이 물리적으로 Cloud 원격 서버에 구동되기 때문입니다.
* **비즈니스 임팩트**: 사내 PC에 GPU가 없어도 최고 성능의 LLM을 돌릴 수 있으며, 무거운 프로그램(게임 엔진 등)과 동시 실행해도 OOM(메모리 부족) 크래시가 절대 나지 않아 인프라 관리 부담이 '0'이 됩니다.
* **로컬 모델과의 트레이드오프**: 클라우드는 하드웨어 셋업 비용이 없지만 트래픽에 비례해 영구적인 토큰 호출 비용($)이 발생합니다. 반면 로컬 모델(Qwen)은 4.42GB의 VRAM을 점유하지만, **보안이 생명인 사내 미공개 빌드 정보나 유저 계정(UID)을 외부로 보내지 않아도 된다**는 압도적 이점이 있습니다.

**2. `N/A (Serverless)`의 해석: 순수 디코딩 속도 측정의 무의미함**
* **의미**: 초당 토큰 생성 속도(TPS)를 순수하게 측정할 수 없다는 뜻입니다.
* **기술적 리뷰**: 로컬 모델은 PC의 GPU 연산 속도를 정확히 잴 수 있으나, 클라우드 API는 ①인터넷 왕복 시간(RTT), ②서버 트래픽 대기열, ③서버 분산 처리 로직이 모두 섞여 들어옵니다. 이를 토큰 수로 나눠 TPS를 구하면 '네트워크 지연이 포함된 체감 속도'가 되어 로컬 TPS와 1:1 비교하는 것 자체가 통계적 오류입니다.
* **결론**: 클라우드 서버의 연산 성능은 강력하지만, 네트워크 지연으로 인해 **최종 지연 시간(Latency, 4.08초)은 로컬(1.39초)보다 2.8배 느렸습니다.** 실시간으로 쏟아지는 인게임 버그 리포트를 즉각 트리아지하려면 순수 처리 속도를 통제할 수 있는 **로컬 모델(Qwen)이 압도적으로 유리하다**는 실측 근거가 됩니다.

### 4) QA 엔지니어링 관점 심층 분석

**1. 정보 부족 대응(Fallback)의 극단적 대조 (Q08 단문 '크래시남')**  
`[ Cloud 압도적 우세 / Qwen 방어적 차선 / Llama 치명적 결함 ]`
* **현상**: 단문 인입 시 Cloud는 성급한 판정을 유보하고 `심각도: 판단보류`, `재현 여부: 불명확`을 선언한 뒤 필수 5대 역질문(시점, 절차, 덤프, OS, 버전)을 출력했습니다. 반면 Llama는 없는 결함과 기기 사양을 완전히 날조(Hallucination)했고, Qwen은 비문 출력 및 소극적 침묵에 그쳤습니다.
* **실무 영향**: Llama의 날조는 버그 데이터베이스를 오염시켜 QA/개발팀 전체의 공수를 낭비시킵니다. Cloud는 이상적인 시니어 QA 대응을 보여주었으며, 로컬 모델 중에서는 소극적이지만 날조하지 않는 Qwen에 퓨샷(Few-Shot) 가드레일을 보완하는 것이 유일한 현실적 대안임을 확인했습니다.
* **판정**: **Cloud 압도적 우세** (로컬 도입 시 Qwen 기반 가드레일 설계의 당위성 확보).

**2. 복합 결함 분할 및 심각도 우선순위 가중치 (Q06 복합 3건)**  
`[ Cloud 독보적 우세 ]`
* **현상**: 3개 결함(로그인 튕김, 상점 미작동, 초대 보상 누락)이 혼재된 리포트에 대해, 로컬 2종은 모두 단일 모듈('UI')로 단순 축소 분류했습니다. 반면 Cloud 모델은 로그인 불가 현상을 즉각 포착하여 심각도를 `Blocker`로 격상하고, 3개 이슈를 개별 분리하여 검증할 것을 지시했습니다.
* **실무 영향**: 단일 티켓으로 묶여 긴급 크래시가 묻히는 실무 사고를 방지하려면 단일 프롬프트 처리보다는, Cloud의 사고 방식을 모사한 **"1차 이슈 스플리터 전처리 파이프라인"** 도입이 필수적입니다.
* **판정**: **Cloud 독보적 우세** (프로덕션 2단계 파이프라인 설계 필요성 입증).

**3. 재현율 판정의 현실성과 검증 신중성 (Q02 결제 미지급)**  
`[ Cloud 우세 ]`
* **현상**: 유저 3명의 신고 문구에 대해 로컬 모델들은 단순 텍스트에 매몰되어 `발생(100%)`으로 단정했습니다. 반면 Cloud 모델은 사내 재현 검증 및 로그 확인이 아직 이루어지지 않은 VOC 단계임을 인지하고 `재현 여부: 불명확`으로 신중하게 판정했습니다.
* **실무 영향**: 외부 리포트를 무조건 확정 버그로 단정하면 담당 엔지니어 배정 후 헛걸음 검증을 초래하므로, 트리아지 단계의 신중한 판정 룰셋이 요구됩니다.
* **판정**: **Cloud 우세** (QA 도메인 맥락 기반의 엄격한 판정 기준 유지).

**4. 유사 결함 및 중복 티켓 감지 역량 (Q10 중복 의심)**  
`[ Cloud & Llama 공동 우세 / Qwen 미흡 ]`
* **현상**: Q01과 연관된 유사 제보에 대해 Cloud와 Llama는 모두 `"이전 신고와의 연관성 및 중복 여부 확인"`을 명확히 명시했습니다. 반면 Qwen은 단순 권장 조치만 나열하며 중복 단서를 누락했습니다.
* **실무 영향**: 중복 티켓 발행 방지 측면에서는 Llama와 Cloud의 맥락 추론 역량이 뛰어나며, Qwen을 실무에 사용할 경우 벡터 DB 기반 유사 티켓 검색(RAG) 전처리가 보완되어야 함을 시사합니다.
* **판정**: **Cloud & Llama 우세** (맥락 인지 및 중복 필터링 역량 입증).

## 6. 결함 및 리스크 분석 (QA Case Study)

### 치명적 결함 사례: Llama-3.1의 Q08 환각(Hallucination)
* **입력값**: `"크래시남"` (단 1단어)
* **Llama-3.1 Run 1 출력**: `[요약]: 게임 내 전투 모드에서 플레이어 캐릭터가 무한히 이동하는 결함 현상 발생`
* **Llama-3.1 Run 2 출력**: `[누락 정보]: Windows 10, Intel Core i5, NVIDIA GeForce GTX 1660 Ti`
* **QA 관점 리스크**:
  * 리포트에 없는 결함 현상과 하드웨어 스펙을 확정적으로 지어내는 환각이 발생했습니다.
  * 이는 실무 버그 트래커에 투입될 경우 존재하지 않는 결함 티켓을 발행하여 개발팀과 QA팀의 리소스를 크게 낭비시킬 수 있는 고위험 결함입니다.

### Qwen2.5의 취약점: 소극적 정보 부족 대응
* 정보가 극도로 부족한 Q08, Q09에 대해 환각을 날조하지는 않았으나, `[누락 정보 및 권장 조치]: 없음`으로 응답하여 테스터에게 추가 정보를 요구해야 하는 트리아지 본연의 목적을 달성하지 못했습니다.
* 이는 프로덕션 도입 전 프롬프트에 Few-Shot 예시를 추가하여 보완해야 할 과제입니다.
