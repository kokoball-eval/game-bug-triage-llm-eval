# v1.4 방법 비교 계획 (사전 등록)

> **상태: 측정 전 확정 (2026-10-04).** 이 문서와 [`method_selection_v14.toml`](../method_selection_v14.toml)은 측정 결과를 보기 전에 커밋한다. 결과를 본 뒤에는 기준과 방법(예시·질문 문구)을 바꾸지 않는다.

## 1. 배경 — 현재 모델이 틀리는 위치

자료는 qwen2.5:7b·프롬프트 v2.3의 기존 실행 기록이다(모델 재선정 seed 1·11·21의 옛 개발용 32건 × 2회 × 3, v1.3 최종 측정의 옛 평가용 31건 × 2회). 옛 평가용 31건은 v1.4에서 개발용으로 바뀌었으므로 설계 근거로 쓸 수 있다. 새 최종 평가용 25건은 보지 않았다.

| 오답 유형 | 응답 수 | 해석 |
| :--- | :---: | :--- |
| X-1 Critical 미상신 | 14 | 반복 악용, 민감 텍스트, 공지와 다른 수치처럼 장애가 눈에 띄지 않는 Critical을 Major로 판정. 규칙은 프롬프트에 있으나 적용하지 못함 |
| 과잉 상신 | 13 | Critical이 아닌 결함과 Critical 이슈의 중복 건을 긴급 사인 요청으로 보냄 |
| 우선순위 오답 | 107 | Trivial을 Minor로 22, 결함이 아닌 글에 Major 18, 정보 부족 단문(판단보류)에 Minor 17, Critical을 Major로 11, Major를 Critical로 7, 기타 32 |

**판정 기준 변경 (측정 전, 2026-10-04):** Minor와 Trivial은 서로 바뀌어도 BTS 처리가 크게 달라지지 않으므로, 첫 정답이 Minor 또는 Trivial인 문항은 다른 쪽도 정답으로 허용한다(기준서 v1.4 §4.1, 개발용 9건·최종 6건 해당). 위 표의 "Trivial을 Minor로 22"는 이 기준에서 오답이 아니다. 우선순위에서 남는 핵심 오답은 **결함이 아닌 글에 등급을 붙이는 것**과 **정보 부족 단문을 판단보류로 두지 않는 것**이다.

오답은 두 갈래다. 하나는 **눈에 띄지 않는 Critical을 알아보지 못하는 것**(X-1)이고, 다른 하나는 **등급 눈금이 전반적으로 한 칸씩 어긋나는 것**(우선순위 정답률 60% 안팎)이다.

## 2. 비교하는 방법

| 방법 | 내용 | 겨냥하는 오답 |
| :---: | :--- | :--- |
| M0 | 기준선. 프롬프트 v2.3 + 형식 재요청 + 폐기 확인 + 후처리 안전장치 g2 | — |
| M1 | M0 + 판정 예시 4개(few-shot) | 등급 눈금 |
| M2 | M0 + Critical 체크리스트(예/아니오 질문 6개, 코드가 Critical 여부 결정) | X-1 |
| M1+M2 | 두 방법을 함께 적용. M1·M2가 모두 채택 대상일 때만 측정 | 두 가지 모두 |

M1·M2는 한 가지씩만 바꾼다. M1은 시스템 프롬프트 뒤에 예시만 더하고, M2는 첫 응답 뒤에 질문 단계만 더한다. 형식 재요청·폐기 확인·안전장치는 모든 방법에서 같다.

### 2.1 M1 — 판정 예시 4개

예시는 판정 기준서의 분류·등급 정의를 그대로 옮긴 가상 리포트다. 평가셋 문항을 고쳐 쓰지 않으며, 88건 어느 문항과도 표현이 겹치지 않는지 테스트로 확인한다(§4).

| 예시 | 입력 | 정답 | 기준서 근거 |
| :---: | :--- | :--- | :--- |
| E1 | (A) "펫 이름 변경권은 어디서 사나요?" 운영 문의 | 문의·건의 / 해당 없음 / CS 응대 / 빈도 해당 없음 | C-3, H-6 |
| E2 | (A) "낚시하면 멈춤" 기기·장소 없는 단문 | 결함 / 판단보류 / 재현 정보 부족 / 정보 요청 후 보류 + 개발 QA 재현 확인 병행 | R-3, H-3a |
| E3 | (B) 내부 QA, 우편함 닫기 버튼 아이콘 2px 어긋남, 재현율 10/10 | 결함 / Trivial / 개발 배정 / 항상 | §4.1 Trivial, H-2b |
| E4 | (A) 계정당 1회인 주간 보상을 캐릭터를 바꿔 가며 여러 번 받음, PC, 세 캐릭터 모두 | 결함 / Critical / 긴급 사인 요청 / 항상 | §4.1(반복 획득 악용), H-1 |

E1·E2는 등급 눈금(해당 없음·판단보류), E3은 QA 작성 이슈의 미관 결함 처리(개발 배정), E4는 눈에 띄지 않는 Critical 유형이다. Minor↔Trivial 상호 허용 이후 E3의 Trivial 등급 자체는 채점에 영향이 작지만, 네 예시의 등급·처리가 서로 달라야 한쪽으로 쏠리지 않으므로 그대로 둔다. 예시 원문과 출력 8칸 전문은 [`docs/method/m1_examples.md`](../docs/method/m1_examples.md)에 확정본으로 두고(검토자 승인 2026-10-04), 실행 코드는 이 문서와 같은 문자열을 쓴다(테스트로 확인). 입력은 문항당 약 2,000 → 3,500 토큰으로 늘며 num_ctx 8,192 안에 들어간다.

**구현 확정 사항 (6단계, 측정 전 2026-10-04):** 예시 블록 첫 줄에 "예시의 기기·수치·상황을 응답에 옮겨 쓰지 마세요"를 둔다(§4 "예시 내용 복사" 대응). 형식 재요청·폐기 확인 질문도 예시를 포함한 같은 앞부분을 쓴다. 예시 문서는 줄바꿈을 LF로 맞춰 읽어, Windows 체크아웃(CRLF)에서도 같은 프롬프트가 된다.

### 2.2 M2 — Critical 체크리스트

첫 응답(형식 재요청 이후)의 [분류]가 결함일 때 아래 질문을 한 번에 묻고, 답은 JSON 스키마로 질문마다 "예"/"아니오"만 받는다. 질문 문구는 기준서 §4.1의 Critical 기준과 프롬프트의 Critical 목록을 옮긴 것이다.

1. 이 현상 때문에 게임 실행·로그인·메인 진행을 할 수 없고, 우회 방법이 없는가?
2. 결제 후 미지급·이중 결제처럼 유료 결제에 피해가 있는가?
3. 캐릭터·아이템·재화 데이터가 사라지거나 이전 상태로 되돌아갔는가?
4. 재화·보상·입장 기회를 반복해서 얻는 악용이 가능하거나, 승패·랭킹 기록이 남지 않는가?
5. 공지된 조정 내용과 실제 수치가 크게 다른가?
6. 여러 유저가 동시에 겪는 서버 장애로 보이는가, 또는 분쟁 지역 명칭·필터를 우회한 욕설처럼 민감한 텍스트 오류인가?

**코드 규칙**

| 첫 응답의 우선순위 | 체크리스트 결과 | 처리 |
| :--- | :--- | :--- |
| Critical 아님 | 하나라도 "예" | [우선순위]를 Critical로 올린다 → 안전장치 H-1이 긴급 사인 요청으로 보낸다 |
| Critical 아님 | 모두 "아니오" | 바꾸지 않는다 |
| Critical | (무관) | 바꾸지 않는다. 답은 기록만 남긴다(과잉 상신 분석용, 내리기 규칙은 v1.5에서 별도 실험) |

- [재현 정보]가 부족하면 6번 중 서버 장애일 때만 올린다(기준서 H-3a: 정보가 부족한 단문은 판단보류 + 정보 요청, H-1b: 서버 장애 의심은 예외).
- [분류]가 중복 의심·결함이 아닌 글은 묻지 않는다.
- **구현 확정 사항 (6단계, 측정 전 2026-10-04):** 6번은 한 질문으로 묻되 답을 "서버 장애 / 민감한 텍스트 / 아니오" 중 하나로 받아, 재현 정보가 부족할 때 서버 장애만 예외로 올리는 규칙을 적용한다. 질문 앞에 "리포트에 적힌 내용만으로 답하고, 확실하지 않으면 아니오"를 둔다. 형식 재요청 뒤, 폐기 확인 앞에 묻는다. 판단 필드가 허용 값 밖이면 바꾸지 않는다(형식 위반을 가리지 않기 위함).
- 모델 원본 응답, 질문과 답, 적용 여부를 실행 기록에 남긴다. [우선순위] 줄만 바꾸고 다른 필드는 그대로 둔다.
- 올리기만 하는 이유: Critical 누락(X-1)은 사고이고 과잉 상신은 리드 QA 사인 업무 증가이므로 손해가 비대칭이다. 또한 올리기와 내리기를 함께 바꾸면 결과가 어느 쪽의 효과인지 나눌 수 없다.

## 3. 측정과 채택 기준

- **데이터:** v1.4 개발용 63건 × 2회, seed 1·11·21. 최종 평가용 25건은 사용하지 않는다.
- **기준선 재측정:** M0도 같은 조건으로 다시 실행한다. 옛 개발용 32건의 응답이 기존 실행 기록과 같은지 확인해 실행 환경의 동일성을 함께 점검한다.
- **채택 기준:** [`method_selection_v14.toml`](../method_selection_v14.toml)

| 구분 | 기준 |
| :--- | :--- |
| 절대 기준 | 호출 성공 100%, 날조 0, 출력 언어 위반(R7) 0, 허용 값 위반(R6) 0, 평균 지연 10초 이하 |
| 기준선 대비 | X-2·X-3 누락이 같은 seed의 M0보다 늘지 않음 |
| 회귀 기준 | X-1 증가 0, 처리·분류 하락 0, 과잉 상신 증가 4 이하, 우선순위 하락 2 이하 등 (64응답 기준 허용폭의 2배, 비율 유지) |
| 결정 | seed 3개 모두 통과 + seed 합계 X-1 누락 감소(같으면 우선순위 정답 증가). 여럿이면 X-1 → 우선순위 → 지연 순 |

**X-2·X-3을 상대 기준으로 두는 이유:** 기준선 M0도 개발용 63건에서 X-3 누락이 있다(v1.3 최종 측정에서 옛 평가용 31건 중 4응답). 0건 절대 기준을 적용하면 M0가 원래 틀리던 문항 때문에 모든 후보가 탈락해, 더 나은 방법을 고를 수 없게 된다. 방법 선택은 "어느 방법이 더 나은가"를 판정하고, "실무에 써도 되는가"(0건 기준)는 최종 측정 보고서에서 따로 판정한다. 이 결정은 M0의 v1.4 개발용 결과를 보기 전에 내렸다.

**실험 B:** 실험 A에서 정해진 방법(없으면 M0)으로 qwen2.5:7b와 gemma4:12b를 같은 데이터·seed·기준으로 비교한다. 모델 재선정(v1.4 1단계)은 옛 개발용 32건과 게이트 절대 기준을 썼으나, 실험 B는 실험 A와 같은 기준을 쓴다. 두 실험의 기준이 다르면 방법과 모델의 효과를 같은 잣대로 비교할 수 없기 때문이다.

**최종 측정:** 실험 A·B로 정해진 방법·모델 조합으로 최종 평가용 25건을 seed 1로 1회 실행한다. 0건 절대 기준 통과 여부와 개발용 대비 차이를 보고한다.

## 4. 알려진 위험과 대응

| 위험 | 내용 | 대응 |
| :--- | :--- | :--- |
| 개발용 맞춤(과적합) | M1 예시 주제와 M2 질문이 개발용 오답 분석에서 나왔고, 채택 판정도 개발용으로 한다. 개발용 개선 폭은 실제보다 크게 나올 수 있다 | 예시·질문은 기준서 정의만 옮기고 특정 문항을 베끼지 않는다. 88건과의 표현 겹침을 테스트로 확인한다. 실제 효과는 한 번도 보지 않은 최종 25건으로 판단하고, 보고서에 과대평가 가능성을 명시한다 |
| 예시 내용 복사 | 모델이 M1 예시의 기기명·수치를 응답에 옮겨 쓸 수 있다. 날조 탐지기는 입력에 없는 사실로 판정한다 | 실제 결함으로 보고 그대로 측정한다(날조 0건 절대 기준). 예시의 고유명사는 평가셋에 나오지 않는 것만 쓴다 |
| 체크리스트 "예" 편향 | 7B 모델이 예/아니오 질문에 "예"로 기우는 경향이 있으면 과잉 상신이 늘어난다 | 회귀 기준(과잉 상신 증가 4 이하)으로 판정한다. 질문별 "예" 비율을 기록한다 |
| 프롬프트 길이 변화의 파급 | v2.2에서 규칙 2줄 추가로 응답 29개가 바뀌었다. 예시 추가는 무관한 문항의 판단도 흔들 수 있다 | 문항 단위 회귀 기준(처리·분류 4응답)으로 판정한다 |
| 후보 수 증가 | 후보가 늘수록 개발용에서 우연히 좋아 보이는 방법을 고를 가능성이 커진다 | 후보를 M1·M2와 조건부 M1+M2로 제한하고, 최종 25건으로 확인한다 |
