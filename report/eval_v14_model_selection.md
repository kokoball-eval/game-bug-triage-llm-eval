# v1.4 모델 재선정 보고서 — 버그 트리아지에 더 맞는 모델이 있는가

> 측정일 2026-10-02~03 · 판정 기록 `data/results/v14/selection_result_v14.json` · 자동 생성 판정표 [`model_selection_v14.md`](model_selection_v14.md)
> 사전 점검 기록 `data/results/v14/screening/screening_20261002_194630.json`(1차), `screening_20261002_234906.json`(2차)
> 본문의 [ML]·[PE]·[LC] 표기는 KANT AI 부트캠프 Private LLM 트랙 과정 기록(TIL) 링크다. ML은 머신러닝, PE는 프롬프트 엔지니어링, LC는 LangChain 과정이며 뒤의 숫자는 학습일이다.

## 요약

- **무엇을 했나** — 버그 트리아지의 요구사항에서 후보 조건을 정하고, 후보 8개를 조건으로 거른 뒤 6개를 사전 점검했다. 점검을 통과한 2개 모델을 현재 모델(qwen2.5:7b)과 같은 조건, seed 3개로 비교했다.
- **결정** — **현재 모델을 유지한다.** 측정 전에 정한 교체 규칙(모든 seed에서 기준 통과 + 개선)을 만족한 후보가 없었다.
- **발견** — gemma4:12b는 판단 지표가 크게 앞섰다(Critical 누락 8→3, 우선순위 정답 119→158, seed 3개 합계). 그러나 처리 단계의 회귀와 경계 건 확정 처리(X-3)가 모든 seed에서 같은 문항에 반복되어 기준을 넘지 못했다. 판단력이 좋은 모델과, 그 판단을 현재 절차에 맞게 처리로 옮기는 모델은 다르다.

## 1. 왜 모델을 다시 보나

v1.3 평가용 최종 측정([`eval_v13_final.md`](eval_v13_final.md))에서 코드로 강제한 형식·절차는 처음 보는 리포트에서도 유지됐지만, 모델 판단(Critical 인식, 우선순위)은 개발용보다 크게 떨어졌다. 판단 문제의 해법은 판단 기준을 전달하는 방법을 바꾸거나, 판단을 더 잘하는 모델로 바꾸는 것이다. 현재 모델은 2024년 9월 공개 모델이라, 이후 공개된 모델 중 이 업무에 더 맞는 모델이 있는지 먼저 확인했다.

두 방법을 동시에 바꾸면 결과가 좋아져도 무엇 덕분인지 알 수 없다. 그래서 파이프라인(프롬프트 v2.3, 형식 재요청, 폐기 확인, 후처리 안전장치 g2)은 그대로 두고 모델만 바꿔 비교했다. 조건 하나만 바꿔 비교한다는 원칙([PE 10/02][pe1002])이다.

"최신 모델 몇 개"가 아니라 버그 트리아지가 모델에 요구하는 것에서 후보 조건을 정했다.

| 8칸 고정 형식으로 BTS에 인입 | 지시 따르기, 구조화 출력(JSON Schema) |

## 3. 사전 점검 — 측정할 수 있는 상태인가

사전 점검(`uv run triage-screen`)은 성능 측정이 아니다. 개발용 3건으로 설치, 생각 끄기, GPU 적재, 구조화 출력, 출력 형식만 확인하고, 3건의 정답률은 계산하지도 기록하지도 않는다. 3건 점수로 후보를 거르면 그 3건에 맞춘 선택이 되기 때문이다. 평가용 문항은 쓰지 않는다. 평가용 세트로 모델을 고르면 평가용이 모델 선택용 연습 문제가 된다(봉인 Test 원칙, [ML 08/14][ml0814]·[ML 08/18][ml0818]).

| 모델 | 결과 | 근거 |
| :--- | :---: | :--- |
| qwen2.5:7b (현재) | PASS | 대조군. 4,888 MiB, 67.9 tok/s |
| gemma4:12b | HOLD → 진행 | 형식 정상. GPU 적재는 사람이 판정(아래) |
| granite4:tiny-h | PASS | 180.9 tok/s. 단, 빈 줄(R4)·필드 반복(R3) 관찰 |
| qwen3.5:9b | FAIL | CPU로 735 MiB 넘침 (`ollama ps` 12%/88% CPU/GPU) |
| gemma4:e4b | FAIL | 필드 이름 없이 값만 출력 (3건 중 2건) |
| qwen3:8b | FAIL | 3건 모두 대괄호 없는 `요약:` 형식 |
| qwen3.5:4b | FAIL | 1건에서 8칸 모두 콜론 누락 |

판정 기준은 결과를 보고 바꾸지 않았다. 콜론 하나가 빠진 정도의 위반도 기준대로 FAIL로 두었다. 결과를 보고 기준을 느슨하게 하면 측정 전에 기준을 정한 의미가 없어진다.

**측정 도구의 결함과 대응** — 1차 점검에서 gemma4 두 모델이 GPU 적재 PASS를 받았지만, 보고된 적재 크기(896 MiB)가 모델 파일(7.4 GB)보다 작고 지연이 현재 모델의 3배였다. Ollama가 gemma4 계열의 크기를 실제와 다르게 보고하고 있었고, 점검 코드가 그 값을 검사 없이 믿은 것이 원인이다([ISSUE-009](../docs/issue_log.md#issue-009), [OBS-003](../docs/issue_log.md#obs-003)). 보고된 크기가 모델 파일보다 작으면 PASS 대신 판정 불가(HOLD)로 두도록 고치고, Ollama와 무관한 nvidia-smi VRAM 사용량과 생성 속도를 함께 기록하게 했다. gemma4:12b는 VRAM 6,762 MiB(전체 8,151 MiB), 31.3 tok/s로 넘침이 없다고 사람이 판정해 비교 측정에 넣었다. 측정 도구가 틀린 값으로 PASS를 내는 것이 측정을 못 하는 것보다 위험하다. 테스트 실무에서 도구의 오판을 도구 결함으로 따로 등록하는 것과 같은 처리다.

## 4. 비교 측정 설계 — 측정 전에 고정한 것

| 항목 | 내용 |
| :--- | :--- |
| 비교 조건 | 평가셋·옵션·문항·반복 횟수에 더해 프롬프트·재요청·폐기 확인·안전장치·생각 끄기 설정까지 같아야 판정 (`triage-select`) |
| 반복 | seed 1·11·21. 같은 seed끼리 짝지어 비교 |
| 절대 기준 | 회귀 게이트와 같음(성공률 100%, 날조·X-2·X-3·R6·R7 0건) + 1건 평균 응답 10초 이하 |
| 회귀 기준 | 회귀 게이트와 같음. 단 지연 증가율(+20%)은 참고로만 기록 |
| 교체 규칙 | 모든 seed에서 기준 통과 → seed 합계로 X-1 누락 감소(같으면 우선순위 정답 증가) → 교체. 개선이 없으면 유지 |

- **지연 기준 10초** — 사람의 BTS 작성 시간(평균 3~5분)에 비해 병목이 되지 않고, 업데이트 직후 제보가 몰려도 PC 1대로 시간당 360건을 처리할 수 있는 값이다. 게이트의 "지연 20% 이하"는 같은 모델에서 프롬프트를 고칠 때의 기준이라 모델 비교에는 쓰지 않았다.
- **기준 값은 복사하지 않았다** — 모델 선택 도구는 절대·회귀 기준 값을 회귀 게이트 기준 파일에서 그대로 읽는다. 값이 두 파일에 있으면 한쪽만 고쳐졌을 때 게이트와 모델 선택이 어긋난다.
- **나빠지지 않은 것만으로 바꾸지 않는다** — 모델 교체에는 지연 증가와 재검증 비용이 든다. 공정한 후보 선정에서 결과를 보기 전에 선정 규칙부터 고정한 것과 같은 방식이다([ML 08/18][ml0818]).

**코드 변경이 측정을 바꾸지 않았는지 먼저 확인했다.** 비교를 위해 `run.py`에 생각 끄기(`think=False`)와 모델별 메모리 해제(OBS-002의 `ollama stop`을 코드로 옮김)를 넣었다. 변경 후 qwen2.5:7b 개발용 seed 1을 다시 실행해 v1.3 실행 기록과 대조한 결과, 모델 원본 응답과 최종 응답이 **64건 모두 같았다**(`v13_dev_20261002_234539.json`). 리팩토링 후 동작 동일성을 확인한 v1.3 구조 정리와 같은 절차다.

**granite4:tiny-h** — 거의 모든 기준에서 떨어졌다. 사전 점검에서 관찰한 빈 줄과 필드 반복이 형식 STRICT를 seed당 4~6건으로 떨어뜨렸고, 출력 길이 상한(512토큰)에 걸린 11건도 모두 이 모델이었다. 날조 판정 6건은 실제 날조다(입력 "아이폰 14 프로"를 "iOS 14"로, 근거 없는 "1회" 빈도).

**gemma4:12b** — 판단 지표는 모두 크게 앞섰지만, 아래 기준에서 모든 seed가 FAIL이었다.

| 걸린 기준 | 문항 | 내용 | 판단 |
| :--- | :--- | :--- | :--- |

날조 판정은 오판이지만, 측정 전에 정한 규칙대로 채점기를 고치지 않았다. **날조를 빼도 X-3·과잉 상신·처리 회귀로 결론은 같다.** 탐지기 결함이 결정을 바꾸지 않는다는 것까지 확인했다.

## 6. 해석

1. **회귀가 우연이 아니라 경향이다.** gemma4:12b의 회귀는 seed 3개에서 거의 같은 문항(A03, A11, A17, B12)에 반복됐다. 샘플링 변동이 아니라 모델의 판단 경향이라는 뜻이다. seed 하나만 봤다면 이 구분을 할 수 없었다.
2. **판단은 좋은데 절차가 맞지 않는다.** gemma4:12b는 분류·우선순위를 더 잘 맞히면서도, 그 판단을 처리로 옮기는 단계에서 현재 판정 기준서와 다르게 움직였다(Critical을 넓게 보는 경향, 광고 글의 처리). 과잉 상신은 Critical 누락보다 피해가 작은 방향이지만, 리드 QA의 사인 업무를 늘리므로 기준 안에서 관리해야 한다.
3. **비교 조건이 현재 모델에 유리했다.** 프롬프트 v2.3은 qwen2.5:7b의 개발용 결과를 보며 다듬었다. 새 모델은 다른 모델에 맞춘 지시문으로 측정된 셈이다([KL-004](../docs/issue_log.md#kl-004)). gemma4:12b의 판단 지표 우위는 이 불리한 조건에서 나온 결과라 의미가 있지만, 그렇다고 지금 프롬프트를 gemma4에 맞추면 모델과 프롬프트를 동시에 바꾸게 된다.

## 7. 결론과 다음 과제

1. **현재 모델(qwen2.5:7b)을 유지한다.** 교체 규칙을 만족한 후보가 없다. 교체가 없으므로 새 평가 문항으로 최종 확인하는 단계는 진행하지 않는다.
2. **"모델 × 판단 기준 전달 방법" 실험의 근거가 생겼다.** v1.4의 다음 과제(KL-003, 판단 기준 전달 방법 비교)에서 gemma4:12b를 함께 후보로 둔다. 모델을 고정하고 전달 방법만 바꾸는 실험과, 전달 방법을 고정하고 모델만 바꾸는 실험을 나눠 한 번에 하나씩 판정한다.
3. **날조 탐지기 수정(ISSUE-008)의 우선순위를 올린다.** 같은 유형의 오판이 다른 모델에서도 재현됐다(qwen2.5 "100번→100회", gemma4 "한 번→1회"). 수정 전후로 저장된 실행 기록 전체의 탐지 결과를 비교해 다른 판정이 바뀌지 않는지 확인한다.
